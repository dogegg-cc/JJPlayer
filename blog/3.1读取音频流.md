# AVChannelLayout

在过去的 FFmpeg 老版本（4.x 及更早版本）中，音频声道是通过一个简单的 64 位整数（`uint64_t channel_layout`）来表示的。但随着现代音频技术的发展（比如杜比全景声、全景环绕声以及超过 64 个声道的复杂工业音频），这种简单的位掩码方式完全不够用了。

因此，从 **FFmpeg 5.0** 开始，官方彻底废弃了旧的整数表示法，引入了一个全新且功能强大的结构体：**`AVChannelLayout`**。

### 1. 结构体本质

`AVChannelLayout` 统一了 FFmpeg 内部所有关于音频声道的描述。它不再是一个单纯的数字，而是一个包含多维信息的结构体：

```c
typedef struct AVChannelLayout {
    enum AVChannelOrder order; // 声道排列的类型（顺序、原生位掩码、无脑非特定等）
    int nb_channels;           // 声道的总数量（例如：双声道就是 2）
    
    union {
        uint64_t mask;         // 当 order 为 NATIVE 时，传统位掩码（如立体声的 LEFT | RIGHT）
        AVChannelCustom *map;  // 当 order 为 CUSTOM 时，支持对每一个声道进行极其硬核的自定义命名和位置描述
    } u;
    
    // 内部隐藏的私有或保留字段...
} AVChannelLayout;
```

### 2. 核心成员与三种声道模式 (`order`)

通过结构体中的 `order` 字段，FFmpeg 将声道管理划分为了不同的段位：

- **`AV_CHANNEL_ORDER_NATIVE`（最常用）**：

  标准的原生声道。它底层依然兼容传统的位掩码。比如标准的立体声（Stereo），它会明确记录这 2 个声道一个是“左声道（Left）”，一个是“右声道（Right）”。

- **`AV_CHANNEL_ORDER_UNSPEC`（无特定描述）**：

  只知道**声道的数量**，但不知道每个声道具体对应现实里的什么方位。常用于某些未知的工业多通道裸音频。

- **`AV_CHANNEL_ORDER_CUSTOM`（硬核自定义）**：

  允许给每一个声道单独起名字、指定任意的物理角度方位。这使得 FFmpeg 能够完美支撑电影院级的多维空间音频。

### 3. 实战：如何初始化与操作 `AVChannelLayout`

在 C/C++ 开发中，你**千万不能**直接给这个结构体的内部变量赋值。FFmpeg 提供了一系列非常优雅且安全的宏和 API 供我们使用：

#### ① 快速初始化常见声道（推荐姿势）

FFmpeg 预设了大量类似 `AV_CHANNEL_LAYOUT_STEREO`（立体声）、`AV_CHANNEL_LAYOUT_5POINT1`（5.1环绕声）的宏。你可以通过 `AV_CHANNEL_LAYOUT_MASK` 或特定函数直接安全地在栈上初始化：

```c
// 初始化一个标准的双声道立体声布局
AVChannelLayout my_layout = AV_CHANNEL_LAYOUT_STEREO;

// 或者使用动态函数（常用于根据声道数量初始化默认布局）
AVChannelLayout default_layout;
av_channel_layout_default(&default_layout, 2); // 自动生成双声道立体声布局
```

#### ② 在 `AVCodecContext`（解码/编码）中的经典用法

在现代 FFmpeg 中，音频解码器吐出的 `AVCodecContext` 或者编码器需要的配置，全部换成了这个结构体。

```c
// 打印解码出来的音频声道信息
printf("音频声道数: %d\n", pCodecCtx->ch_layout.nb_channels);

// 将一个声道布局完美复制给另一个（会自动处理内部指针和内存）
AVChannelLayout dst_layout;
av_channel_layout_copy(&dst_layout, &pCodecCtx->ch_layout);

// 记得不用的时候释放它（尤其是包含自定义 CUSTOM 布局时，防止内存泄漏）
av_channel_layout_uninit(&dst_layout);
```

#### ③ 获取人类能读懂的字符串描述

如果你想在 UI 界面上或者日志里打印出这个音频流到底是“立体声”还是“5.1 环绕声”，可以使用 `av_channel_layout_describe`：

```c
char buf[64];
// 自动将布局转成字符串，比如输出 "stereo" 或 "5.1" 或 "7.1"
av_channel_layout_describe(&pCodecCtx->ch_layout, buf, sizeof(buf));
printf("当前音频声道布局为: %s\n", buf);
```

### 4. 迁移与避坑指南（老版本 vs 新版本）

如果你正在重构一段几年前的老代码，或者在网上参考了旧教程，你一定会遇到编译报错。请参照以下表格进行安全替换：

| **历史旧写法 (≤ FFmpeg 4.x)**       | **现代标准写法 (≥ FFmpeg 5.x / 6.x / 7.x)**                  |
| ----------------------------------- | ------------------------------------------------------------ |
| `pCodecCtx->channels`               | `pCodecCtx->ch_layout.nb_channels`                           |
| `pCodecCtx->channel_layout`         | 换为整个结构体操作，或通过 `pCodecCtx->ch_layout.u.mask` 获取 |
| `av_get_default_channel_layout(2)`  | `av_channel_layout_default(&layout, 2)`                      |
| `av_get_channel_layout_string(...)` | `av_channel_layout_describe(...)`                            |

> **⚠️ 核心安全警示：**
>
> 任何时候只要你使用了 `av_channel_layout_copy()` 或者通过 API 改变了其内部结构，在不需要它的时候，**必须**调用 **`av_channel_layout_uninit(&layout)`** 进行复位释放。否则，一旦遇到使用了 `CUSTOM` 模式的复杂音频流，其内部动态分配的 `map` 指针将导致隐蔽的内存泄漏。

### 总结

`AVChannelLayout` 的引入虽然在刚升级时给开发者带来了一点点代码重构的麻烦，但它彻底让 FFmpeg 的音频架构迈入了现代空间音频的梯队。



# swr_alloc_set_opts2

在 FFmpeg 的音频处理世界中，**swr_alloc_set_opts2** 是负责音频重采样（Resampling）的灵魂函数。

当解码出来的原始音频（PCM）与你的播放设备（声卡）或者目标编码器要求的参数不匹配时——例如，解码出来的是 **5.1 声道 / 48000Hz / 浮点型（FLTP）** 格式，而你的声卡只支持 **双声道（Stereo）/ 44100Hz / 16位整型（S16）**——你就必须搭建一个“音频加工厂”来做转换。这个函数就是用来配置和创建这个加工厂（SwrContext）的。

### 1. 时代背景：为什么名字后面有个“2”？

如果你参考了旧教程，你可能会看到 swr_alloc_set_opts（没有2）。

由于我们在上一步提到了 **FFmpeg 5.0 彻底废弃了旧的整数声道掩码，改用 AVChannelLayout 结构体**，导致原有的重采样配置函数参数直接失效。

为了兼容新时代的音频架构，FFmpeg 在 5.1 版本中推出了全新的 **swr_alloc_set_opts2**，成为了现代 FFmpeg 音频开发的标准 API。

### 2. 函数原型

```c
int swr_alloc_set_opts2(
    struct SwrContext **ps,                  // 输出：指向 SwrContext 指针的指针
    const AVChannelLayout *out_ch_layout,    // 输出：目标声道布局
    enum AVSampleFormat out_sample_fmt,      // 输出：目标采样格式（如 AV_SAMPLE_FMT_S16）
    int out_sample_rate,                     // 输出：目标采样率（如 44100）
    const AVChannelLayout *in_ch_layout,     // 输入：原始源声道布局
    enum AVSampleFormat in_sample_fmt,       // 输入：原始源采样格式
    int in_sample_rate,                      // 输入：原始源采样率
    int log_offset,                          // 日志偏移量，通常填 0
    void *log_ctx                            // 日志上下文，通常填 NULL
);
```

- **返回值**：成功时返回 0，失败时返回一个负数的错误码。

### 3. 实战：标准重采样初始化“三步走”

在多媒体开发中，配置好重采样上下文后，还需要将其正式激活。标准的流程如下：

```c
struct SwrContext *swr_ctx = NULL; // 核心上下文

// 1. 设定你期望的输出参数（假设你的声卡只认 44100Hz S16 立体声）
AVChannelLayout out_layout = AV_CHANNEL_LAYOUT_STEREO;
enum AVSampleFormat out_fmt = AV_SAMPLE_FMT_S16;
int out_rate = 44100;

// 2. 假设输入参数（in_layout, in_fmt, in_rate）来自于音频解码器（AVCodecContext）
// 调用函数进行分配和参数绑定
int ret = swr_alloc_set_opts2(
    &swr_ctx,                // 传入指针的地址，函数内部会为其分配合适的堆内存
    &out_layout, out_fmt, out_rate,   // 目标参数
    &pCodecCtx->ch_layout, pCodecCtx->sample_fmt, pCodecCtx->sample_rate, // 原始输入参数
    0, NULL
);

if (ret < 0 || !swr_ctx) {
    printf("音频重采样上下文分配失败！\n");
    return -1;
}

// 3. 极其重要：刚刚只是配置了参数，必须拉闸开工，正式初始化
ret = swr_init(swr_ctx);
if (ret < 0) {
    printf("音频重采样初始化失败！\n");
    swr_free(&swr_ctx);
    return -1;
}

// 此时 swr_ctx 已经完全准备就绪，后续可以在解码循环里用 swr_convert() 搬运像素/采样了！
```

### 4. 核心优化与避坑指南

#### ① AV_SAMPLE_FMT_FLTP 的平面陷阱

现代 FFmpeg 解码器（如 AAC、MP3）解码出来的音频数据几乎全都是 **Planar（平面）** 格式，比如 FLTP（带 P 结尾）。这意味着左声道的所有声音在一个数组里，右声道的在另一个数组里。

但是，**绝大多数系统的底层音频驱动（如 Windows 的 DirectSound、SDL2 库、Linux 的 ALSA）只认 Packed（打包/交织）** 格式，比如 S16。这就要求你在调用 swr_alloc_set_opts2 时，输出格式千万别习惯性带 P，必须转成非 P 格式，让重采样库在转换时顺便把数据交织好。

#### ② 动态重连机制

如果你的播放器需要支持无缝切歌，且两首歌的采样率不同（比如第一首 44100Hz，第二首 48000Hz），你可以重复利用这个函数：

```c
// 如果 swr_ctx 已经存在，再次调用 swr_alloc_set_opts2 
// 它会在内部自动调整参数并安全更新，之后只需重新调用一次 swr_init() 即可，无需销毁重来。
swr_alloc_set_opts2(&swr_ctx, &out_layout, ...);
swr_init(swr_ctx);
```

#### ③ 内存释放别用错

当播放结束或者销毁播放器时，释放该上下文必须调用配套的专用函数：

```c
// 释放内存并将指针安全置为空，防止野指针
swr_free(&swr_ctx);
```

### 总结对比

| **模块类型**     | **视频转换上下文**                    | **音频转换上下文**  |
| ---------------- | ------------------------------------- | ------------------- |
| **核心结构体**   | SwsContext                            | SwrContext          |
| **分配配置函数** | sws_getContext / sws_getCachedContext | swr_alloc_set_opts2 |
| **核心转换动作** | sws_scale                             | swr_convert         |

至此，你不仅通关了 FFmpeg 视频像素的处理，连音频的通道、重采样处理也全部斩获。



# swr_get_delay与av_rescale_rnd

在进行音频重采样时，**`swr_get_delay`** 和 **`av_rescale_rnd`** 是两个为了解决“音视频不同步（卡顿/撕裂）”**和**“时间戳精准换算”而必须联合使用的硬核函数。

当你在音频重采样的循环里发现“为什么播放声音总是断断续续有杂音”或者“声音越播越慢”时，通常就是因为没有处理好这两个函数背后的逻辑。

### 1. swr_get_delay：解决音频重采样的“历史残留”问题

#### 为什么需要它？

音频重采样（比如把 $48000\text{Hz}$ 降频到 $44100\text{Hz}$）本质上是通过数学算法在信号上进行插值计算。

由于算法需要参考前后多个采样点，`SwrContext` 内部会维护一个**输入缓冲区**。这意味着：**你每次喂给重采样器 $1024$ 个采样点，它内部可能会扣留几十个点留在缓冲区里，用于和下一次输入的数据一起做连贯性计算。**

如果你在计算输出内存大小时，只根据当前输入的 $1024$ 个点去分配，久而久之，留在重采样器内部的“历史残留点”就会越来越多，导致声音产生断续的噪点或逐渐累积延迟。

#### 函数原型

```c
int64_t swr_get_delay(struct SwrContext *s, int64_t base);
```

- **`base`**：时间基准。
  - 如果你想知道**内部还剩多少个输入的采样点**没吐出来，传**输入采样率**（如 $48000$）。
  - 如果你想知道**内部剩的这些点，换算成输出采样率是多少个点**，传**输出采样率**（如 $44100$）。

### 2. av_rescale_rnd：绝对精准的时钟换算器

#### 为什么需要它？

我们在计算重采样输出需要分配多大的内存缓冲区时，公式理论上是：

$$\text{输出采样数} = \text{输入采样数} \times \frac{\text{输出采样率}}{\text{输入采样率}}$$

但是，在 C/C++ 中，整数除法会直接**丢弃小数部分（向下取整）**。在每秒几十次的音频处理循环中，每次丢弃微小的精度，积少成多，播放几分钟后音频时钟就会彻底错乱。

`av_rescale_rnd` 是 FFmpeg 专门为了**防止整数运算由于四舍五入导致精度丢失**而设计的数学工具函数。它利用了 `int64_t` 内部进行大数运算，保证换算结果绝对精准。

#### 函数原型

```c
int64_t av_rescale_rnd(int64_t a, int64_t b, int64_t c, enum AVRounding rnd);
```

- **计算公式**：$\text{返回结果} = a \times \frac{b}{c}$，并根据 `rnd` 规则进行舍入。
- **`rnd` 常用取值**：`AV_ROUND_UP`（向上取整）或 `AV_ROUND_NEAR_INF`（四舍五入）。在分配内存缓冲区时，为了绝对安全，**强烈建议使用 `AV_ROUND_UP`（宁可多分配一点，绝不越界崩溃）**。

### 3. 梦幻联动：如何完美计算重采样的输出缓冲区大小？

在实际的音频解码重采样循环中，这两个函数必须像下面这样组合使用，才能完美动态地计算出这一帧到底能生成多少个输出采样点：

```c
// 假设当前解出了一帧音频：in_frame

// 1. 获取重采样器内部“历史残留”的输入采样点数，并立刻换算成“输出采样率下的点数”
int64_t delay_samples = swr_get_delay(swr_ctx, out_sample_rate);

// 2. 使用 av_rescale_rnd 精准计算：当前的输入采样数，在输出采样率下应该对应多少个点
// 公式：out_samples = in_samples * out_rate / in_rate (向上取整)
int64_t current_out_samples = av_rescale_rnd(
    in_frame->nb_samples, 
    out_sample_rate, 
    in_frame->sample_rate, 
    AV_ROUND_UP
);

// 3. 总共期望输出的采样点数 = 缓存残留点数 + 当前帧换算点数
int max_out_samples = delay_samples + current_out_samples;

// 4. 根据计算出的 max_out_samples，去动态分配合适的内存空间
// 比如使用 av_samples_alloc 或调整你的 pcm_buffer 大小
int out_linesize;
uint8_t **out_data = NULL;
av_samples_alloc(&out_data, &out_linesize, out_ch_layout.nb_channels, 
                 max_out_samples, out_sample_fmt, 0);

// 5. 正式调用重采样转换
// swr_convert 的第 4 个参数传入刚刚计算出来的 max_out_samples
int real_out_samples = swr_convert(
    swr_ctx,
    out_data, max_out_samples, // 目标空间和最大容量
    (const uint8_t **)in_frame->data, in_frame->nb_samples // 源数据和源点数
);

// real_out_samples 是重采样器真正吐出来的点数，通常 <= max_out_samples
// 接下来你就可以把 out_data 里长度为 real_out_samples 的数据丢给声卡播放了！

// 6. 记得释放临时分配的内存
av_freep(&out_data[0]);
av_freep(&out_data);
```

### 4. 衍生面试题：av_rescale_rnd 在时间戳（PTS）换算中的应用

除了音频采样率转换，`av_rescale_rnd` 还有另一个一模一样重要的场景：**换算音视频的时间戳。**

比如，你解码出来一帧视频，它的 `frame->pts` 是基于解码器的 `codec_ctx->time_base`（比如 $1/25$）。但是，当你准备把它写入 MP4 文件时，文件的 `stream->time_base` 可能是 $1/90000$。你必须通过它进行无损换算，否则写进去的视频播放速度会快进或卡死：

```c
// 将视频帧的时间戳从“解码器时间基”无损换算为“容器流时间基”
packet->pts = av_rescale_rnd(
    frame->pts, 
    stream->time_base.den, // 目标的倒数
    codec_ctx->time_base.den, 
    AV_ROUND_NEAR_INF // 时间戳换算通常用四舍五入
);
```

### 总结表格

| **函数**             | **解决的核心问题**                 | **开发中的核心用途**                                      |
| -------------------- | ---------------------------------- | --------------------------------------------------------- |
| **`swr_get_delay`**  | 重采样算法内部的数据积压（扣留点） | 动态累加缓存，防止音频重采样断流和杂音                    |
| **`av_rescale_rnd`** | 整数除法丢弃小数导致的精度灾难     | ① 精准换算采样点（分配内存） ② 精准换算 PTS（音视频同步） |

到这里，你已经接触到了 FFmpeg 音频开发中最容易让初学者劝退的“时间与缓冲区数学计算”部分。把这两个函数吃透，你的播放器音频模块在面对各种奇葩采样率的文件时，就能表现得非常健壮和流畅了。



# swr_convert

在 FFmpeg 的音频处理流水线中，**`swr_convert`** 是真正的“前线重度劳模”。

前面我们通过 `swr_alloc_set_opts2` 规划好了音频加工厂的设备参数，通过 `swr_init` 启动了流水线，并通过 `swr_get_delay` 计算好了需要准备多大的盘子。而 **`swr_convert` 就是那个真正开始把输入的原始 PCM 数据加工（重采样、混音、格式转换）并吐出目标 PCM 数据的函数。**

### 1. 函数原型

```c
int swr_convert(
    struct SwrContext *s,           // 1. 已经初始化好的重采样上下文
    uint8_t **out,                  // 2. 输出缓冲区指针数组（盛放加工后的数据）
    int out_count,                  // 3. 输出缓冲区期望接收的最大采样点数（容量限制）
    const uint8_t **in,             // 4. 输入缓冲区指针数组（源压缩/原始PCM数据）
    int in_count                    // 5. 当前输入的单通道采样点数
);
```

#### 📌 返回值（极其重要）：

- **成功**：返回**实际写入到 `out` 缓冲区的单通道采样点数**（通常 $\le \text{out\_count}$）。
- **失败**：返回一个负数的错误码。

### 2. 参数中的指针数组 (`uint8_t `) 怎么传？

这是初学者遇到 `swr_convert` 时最头疼的地方。为什么输入和输出都是“二级指针”？这跟音频的存储格式（Packed vs Planar）密切相关：

#### ① 如果输出目标是 Packed 格式（交织格式，如 `AV_SAMPLE_FMT_S16`）：

左右声道数据是交替挤在同一个连续内存块里的（`L R L R L R...`）。

- 你只需要分配一个一维的内存块给 `out[0]`。
- 传参时写成：`out`。

#### ② 如果输出目标是 Planar 格式（平面格式，如 `AV_SAMPLE_FMT_FLTP`）：

每个声道的数据独立呆在自己的内存切片里（`out[0]` 全是左，`out[1]` 全是右）。

- 你需要分配一个指针数组，分别指向各自声道的内存。
- 传参时同样写成：`out`。

> **💡 省心小技巧**：在实际开发中，强烈建议使用 **`av_samples_alloc`** 或者 **`av_samples_fill_arrays`** 来帮你自动管理这个二级指针数组的内存分配，免去手动写 `malloc` 的痛苦和越界风险。

### 3. 经典实战：在解码循环中的完整闭环

让我们把之前学到的 `swr_get_delay`、`av_rescale_rnd` 和 `swr_convert` 完美拼装起来，看看它在主循环里的标准姿势：

```c
// 【主循环内】假设已经解出了一帧音频：in_frame

// 1. 精准计算出本次重采样“最大可能吐出”的采样点数（包含内部残留）
int64_t delay_samples = swr_get_delay(swr_ctx, out_sample_rate);
int64_t current_out_samples = av_rescale_rnd(
    in_frame->nb_samples, out_sample_rate, in_frame->sample_rate, AV_ROUND_UP
);
int max_out_samples = delay_samples + current_out_samples;

// 2. 借助 FFmpeg 的安全工具动态分配输出大盘子（指针数组）
uint8_t **out_buffer = NULL;
int out_linesize = 0;
av_samples_alloc(&out_buffer, &out_linesize, 
                 out_ch_layout.nb_channels, // 目标声道数
                 max_out_samples,           // 刚才算出的最大点数容量
                 out_sample_fmt, 0);        // 目标采样格式

// 3. 正式拉闸：开工转换！
int real_out_samples = swr_convert(
    swr_ctx,
    out_buffer, max_out_samples,             // 输出盘子和它的容量限制
    (const uint8_t **)in_frame->data, in_frame->nb_samples // 输入原始数据和当前点数
);

if (real_out_samples < 0) {
    printf("音频重采样转换失败！\n");
} else {
    // 4. 关键时刻：此时 out_buffer 里面已经躺着真正转换好的、长度为 real_out_samples 的 PCM 数据了
    // 如果是对接 SDL2 播放，你可以计算它的总字节数：
    int data_size = av_samples_get_buffer_size(
        NULL, out_ch_layout.nb_channels, real_out_samples, out_sample_fmt, 1
    );
    
    // 把 out_buffer[0] 里的 data_size 字节数据塞给你的播放音频队列...
}

// 5. 转换完一帧，及时释放临时分配的二级指针和内存块
if (out_buffer) {
    av_freep(&out_buffer[0]);
    av_freep(&out_buffer);
}
```

### 4. 进阶大招：“冲刷（Flush）”重采样器

在视频文件播放到末尾、或者音频流结束的时候，很多初学者会发现**最后几百毫秒的声音莫名其妙丢了，或者播放器卡在最后不退出**。

这是因为正如我们在 `swr_get_delay` 中讲的，重采样算法内部还会扣留（缓存）最后一小段采样点。如果文件读完了，你不再喂数据，它就会永远憋在里面。

#### 🚀 正确的收尾姿势（Flush 机制）：

当 `av_read_frame` 读完文件退出循环后，你需要专门进行一次“空转冲刷”，把里面的残余数据全部榨出来：

```c
// 传 NULL 和 0，代表“我没新数据了，把内部憋着的老数据全吐出来吧！”
int flush_samples = swr_convert(swr_ctx, out_buffer, max_out_samples, NULL, 0);

if (flush_samples > 0) {
    // 最后一波“余音”，依然可以送去给声卡播放
}
```

### 5. 常见避坑指南

1. **输入/输出单通道采样点数（nb_samples）的理解**：

   `in_count` 和返回的 `real_out_samples` 代表的是**单通道的采样点数**，千万不要误乘以声道数！比如一帧双声道的音频有 $1024$ 个立体声采样，那它在物理上其实有 $1024 \times 2 = 2048$ 个采样值，但在传递给 `swr_convert` 时，参数必须填 **`1024`**。

2. **容量不足导致的截断**：

   如果你给的 `out_count` 偏小，`swr_convert` 只会把你的输出盘子装满，剩下的数据会继续积压在重采样内部缓冲区里，导致你的音频输出整体出现奇怪的“延迟感”或者在下次转换时发生不可预知的错位。

### 总结

`swr_convert` 是音频管线中计算最密集的点（尤其是涉及声道矩阵混音和高低频重采样时）。只要确保它的**缓冲区大小计算正确**，并在**音频结束时进行了 Flush 处理**，你的 FFmpeg 音频处理模块就几乎达到了工业级的健壮度。

到这里，你已经把从打开输入流、查找解码器、解出压缩包、还原成原始帧、再到音视频像素/重采样像素加工的整个 FFmpeg 脉络**彻底打通了**！



# AudioStreamBasicDescription

当我们把视线从 FFmpeg 的跨平台音频世界（`SwrContext`、`AVChannelLayout`）切回到 **Apple 生态圈（iOS / macOS / watchOS / tvOS）** 时，你会遇到一个出镜率 100% 的底层核心音频结构体：**`AudioStreamBasicDescription`**（开发者们通常亲切地称它为 **ASBD**）。

它是 Apple Core Audio 框架的基石。在 iOS/macOS 上，无论是使用 `AudioQueue` 播放音频、用 `AudioUnit` 做低延迟混音，还是用 `AVAssetReader` 读取音频，你都必须用 ASBD 来**精确描述音频流的物理格式细节**。

### 1. 结构体原型

ASBD 的定义非常严谨，包含了 9 个核心成员变量：

```c
struct AudioStreamBasicDescription {
    Float64 mSampleRate;       // 1. 采样率 (如 44100.0)
    FormatID mFormatID;        // 2. 格式 ID (如 kAudioFormatLinearPCM)
    FormatFlags mFormatFlags;  // 3. 格式元标记 (控制是整型还是浮点、交织还是平面)
    UInt32 mBytesPerPacket;    // 4. 每个 Packet (数据包) 的字节数
    UInt32 mFramesPerPacket;   // 5. 每个 Packet 包含的 Frame (音频帧) 数
    UInt32 mBytesPerFrame;     // 6. 每个 Frame 的字节数
    UInt32 mChannelsPerFrame;  // 7. 声道数 (如 2 代表立体声)
    UInt32 mBitsPerChannel;    // 8. 每个声道采样点的位数 (如 16 位或 32 位)
    UInt32 mReserved;          // 9. 保留对齐字段 (固定填 0)
};
typedef struct AudioStreamBasicDescription AudioStreamBasicDescription;
```

### 2. 理清 Apple 的音频核心概念：Packet、Frame、Sample

在看懂 ASBD 之前，必须先理清 Apple 官方对音频层级的特殊定义（这和 FFmpeg 略有不同）：

- **Sample（采样点）**：单通道中一个最小的音频测算数值。
- **Frame（音频帧）**：在**同一个时间点上**，所有声道的 Sample 集合。如果是双声道立体声，1 个 Frame 里面就包含 2 个 Sample（左和右）。
- **Packet（数据包）**：由一个或多个 Frame 组成。
  - 对于 **PCM（未压缩）** 音频：1 个 Packet 永远等于 1 个 Frame。
  - 对于 **AAC / MP3（压缩）** 音频：一个 Packet 包含上千个 Frame（例如 AAC 一个 Packet 固定包含 1024 个 Frame）。

### 3. 实战：如何正确计算并填写 ASBD 的各项参数？

手动填写 ASBD 极其容易因为数学计算错误导致系统报错。我们以最常用的**未压缩线性 PCM** 格式为例，看看这些参数该如何推导：

#### 场景 A：16位整型、双声道、交织格式（Packed，最常见的常规 PCM）

交织格式意味着左右声道数据是交替挤在同一个内存块里的。

```objective-c
AudioStreamBasicDescription asbd = {0}; // 强烈建议先清零！

asbd.mSampleRate       = 44100.0;
asbd.mFormatID         = kAudioFormatLinearPCM;
// 标记：它是整型、带符号的（Signed）、并且是 Packed（交织格式）
asbd.mFormatFlags      = kAudioFormatFlagIsSignedInteger | kAudioFormatFlagIsPacked;
asbd.mChannelsPerFrame = 2;  // 双声道
asbd.mBitsPerChannel   = 16; // 16位

// 【核心数学计算】
// 1个 Frame 包含2个声道，每个声道16位(2字节)，所以 1 Frame = 2 * 2 = 4 字节
asbd.mBytesPerFrame    = (asbd.mBitsPerChannel / 8) * asbd.mChannelsPerFrame; 
// 因为是未压缩的 PCM，1个 Packet 就是 1个 Frame
asbd.mFramesPerPacket  = 1; 
// 1个 Packet 的字节数 = 1 * 4 = 4 字节
asbd.mBytesPerPacket   = asbd.mFramesPerPacket * asbd.mBytesPerFrame;
```

#### 场景 B：32位浮点型、双声道、非交织格式（Non-Packed/Planar，iOS 硬件首选）

iOS 内部（如 AudioUnit）为了极高的计算精度，底层最喜欢的其实是 **Planar 格式**。也就是说，每个声道有自己独立的内存数组，互不干扰。

```objective-c
AudioStreamBasicDescription asbd = {0};

asbd.mSampleRate       = 44100.0;
asbd.mFormatID         = kAudioFormatLinearPCM;
// 标记：它是浮点数（Float）、并且是 NonInterleaved（非交织/平面格式）
asbd.mFormatFlags      = kAudioFormatFlagIsFloat | kAudioFormatFlagIsNonInterleaved;
asbd.mChannelsPerFrame = 2;
asbd.mBitsPerChannel   = 32; // 32位浮点

// 【Planar 格式下的魔鬼细节】
// 在 Apple 的定义中，如果是 NonInterleaved，mBytesPerFrame 存的是【单通道】一帧的大小！
// 32位 = 4字节，所以这里直接填 4（不用乘以声道数！）
asbd.mBytesPerFrame    = asbd.mBitsPerChannel / 8; 
asbd.mFramesPerPacket  = 1;
asbd.mBytesPerPacket   = asbd.mBytesPerFrame * asbd.mFramesPerPacket;
```

### 4. 梦幻联动：它如何与 FFmpeg 完美对接？

如果你在 iOS 上写播放器，通过 FFmpeg 解码出了 `AVFrame` 并且通过 `swr_convert` 重采样好了 PCM 数据，当你准备把这些数据丢给 iOS 的 `AudioQueue` 播放时，你需要搭建一座参数桥梁：

| **参数含义**     | **FFmpeg 侧（重采样后）**           | **Apple 侧 (ASBD 结构体)**                                   |
| ---------------- | ----------------------------------- | ------------------------------------------------------------ |
| **采样率**       | `out_sample_rate`                   | `asbd.mSampleRate`                                           |
| **声道数**       | `out_ch_layout.nb_channels`         | `asbd.mChannelsPerFrame`                                     |
| **位深度与格式** | `AV_SAMPLE_FMT_S16` (16位整型)      | `asbd.mBitsPerChannel = 16` `asbd.mFormatFlags = ...IsSignedInteger | ...IsPacked` |
| **位深度与格式** | `AV_SAMPLE_FMT_FLTP` (32位平面浮点) | `asbd.mBitsPerChannel = 32` `asbd.mFormatFlags = ...IsFloat | ...IsNonInterleaved` |

### 5. 官方作弊工具（避免手算报错）

因为手算这些 `mBytesPerFrame` 太容易抓狂，Core Audio 官方其实内置了一些快捷宏函数。只要你告诉它基本的位深和声道，它能自动帮你把那堆复杂的 Stride/Packet 字节数全部算好：

```objective-c
AudioStreamBasicDescription asbd;
// 快速填充一个标准的立体声、16位整型 PCM 格式
FillOutASBDForLPCM(asbd, 
                   44100.0,                                 // 采样率
                   2,                                       // 声道数
                   16,                                      // 位深
                   16,                                      // 每一个有效位深
                   false,                                   // 是否是浮点数
                   false);                                  // 是否是大端序 (iOS通常是小端序，传false)
```

### 总结

ASBD 就像是 Apple 音频世界的“物理规格说明书”。任何音频数据在流入或流出 iOS 硬件系统时，都必须佩戴这样一张规格卡片。

搞懂了 ASBD，你就可以在 iOS 上放心大胆地去把玩最底层的 **`AudioUnit`** 或者普通的 **`AudioQueue`** 了。你目前的业务场景，是在用 FFmpeg 解码后把 PCM 喂给 iOS 系统的音频组件进行播放，还是在采集 iOS 麦克风的声音准备塞给 FFmpeg 编码？



# AudioQueueNewOutput

在 Apple 的 Core Audio 框架中，如果你需要播放音频（尤其是那种源源不断、实时解码出来的音频流），**`AudioQueueNewOutput`** 就是你要调用的核心入口函数。

它的主要任务是：**创建一个用于音频输出（播放）的音频队列（Audio Queue）。**

在 iOS/macOS 播放器开发中，它扮演着“中间传送带”的角色。你负责把 FFmpeg 或其他地方解码出来的原始 PCM 数据装进传送带（Buffer）里，而 `AudioQueueNewOutput` 创建的队列则负责把这些 Buffer 均匀、流畅地喂给系统的硬件声卡。

### 1. 函数原型

```c
OSStatus AudioQueueNewOutput(
    const AudioStreamBasicDescription *inFormat,      // 1. 输入的音频物理规格 (ASBD)
    AudioQueueOutputCallback inCallbackProc,          // 2. 极其核心的“索要数据”回调函数
    void * _Nullable inUserData,                       // 3. 传给回调函数的自定义上下文指针
    CFRunLoopRef _Nullable inCallbackRunLoop,         // 4. 回调函数触发的 RunLoop (传 NULL 为默认)
    CFStringRef _Nullable inCallbackRunLoopMode,      // 5. RunLoop 模式 (传 NULL 为默认)
    UInt32 inFlags,                                   // 6. 保留标记 (固定传 0)
    AudioQueueRef  _Nullable * _Nonnull outAQ         // 7. 输出：创建成功的音频队列句柄
);
```

- **返回值 (`OSStatus`)**：如果成功返回 `noErr` (也就是 `0`)，失败则返回相应的错误码（如格式不支持等）。

### 2. 核心灵魂：`AudioQueueOutputCallback` 回调机制

很多初学者容易在这里绕晕：音频队列不是我主动把数据“推”给它吗？为什么还要传一个回调函数？

其实，AudioQueue 采用的是 **“拉（Pull）” 模型**。

1. 你在初始化时，需要向队列申请 3 个左右的空缓冲区（AudioQueueBufferRef）。
2. 你先手动把这 3 个缓冲区填满 PCM 数据，并塞给队列（这叫预热）。
3. 当队列开始播放后，声卡每播完一个缓冲区，这个缓冲区就变空了。
4. 队列底层会**立刻自动触发你传进去的这个回调函数**，对你说：“**服务员，第 X 号盘子空了，请立刻再切点肉（PCM数据）放进来！**”

#### 🛠️ 回调函数的标准写法：

```objective-c
static void MyAudioQueueOutputCallback(void *inUserData, 
                                       AudioQueueRef inAQ, 
                                       AudioQueueBufferRef inBuffer) {
    // 1. inUserData 通常是你自己的播放器类/结构体对象
    MyPlayer *player = (__bridge MyPlayer *)inUserData;
    
    // 2. 从你自己的解码队列（比如 FFmpeg 解码出的音频重采样队列）里读取 PCM 数据
    int bytesRead = [player getPCMData:inBuffer->mAudioData maxSize:inBuffer->mAudioDataBytesCapacity];
    
    if (bytesRead > 0) {
        inBuffer->mAudioDataByteSize = bytesRead;
        // 3. 重新把填满数据的盘子塞回音频队列继续播放
        AudioQueueEnqueueBuffer(inAQ, inBuffer, 0, NULL);
    } else {
        // 如果没数据了（比如播放结束），可以塞入静音数据或者停止队列
        memset(inBuffer->mAudioData, 0, inBuffer->mAudioDataBytesCapacity);
        inBuffer->mAudioDataByteSize = inBuffer->mAudioDataBytesCapacity;
        AudioQueueEnqueueBuffer(inAQ, inBuffer, 0, NULL);
    }
}
```

### 3. 实战：从创建到播放的完整业务闭环

让我们把之前学到的 **ASBD** 和 **`AudioQueueNewOutput`** 串联起来，看看一个播放器音频输出端的标准初始化流程：

```objective-c
AudioQueueRef mAudioQueue = NULL;
AudioQueueBufferRef mBuffers[3]; // 经典的 3 缓冲区机制

// 1. 准备好你的音频规格描述（假设是通过 FFmpeg 重采样好的 44100Hz S16 立体声）
AudioStreamBasicDescription asbd = {0};
asbd.mSampleRate       = 44100.0;
asbd.mFormatID         = kAudioFormatLinearPCM;
asbd.mFormatFlags      = kAudioFormatFlagIsSignedInteger | kAudioFormatFlagIsPacked;
asbd.mChannelsPerFrame = 2;
asbd.mBitsPerChannel   = 16;
asbd.mBytesPerFrame    = 4;
asbd.mFramesPerPacket  = 1;
asbd.mBytesPerPacket   = 4;

// 2. 创建音频输出队列
OSStatus status = AudioQueueNewOutput(&asbd, 
                                      MyAudioQueueOutputCallback, 
                                      (__bridge void *)(self), // 把自己作为上下文传过去
                                      NULL, NULL, 0, 
                                      &mAudioQueue);

if (status != noErr) {
    NSLog(@"创建 AudioQueue 失败，错误码: %d", (int)status);
    return;
}

// 3. 为队列分配物理缓冲区（通常准备 3 个，大小根据业务定，比如每个 10KB 左右）
UInt32 bufferSize = 10240; 
for (int i = 0; i < 3; i++) {
    AudioQueueAllocateBuffer(mAudioQueue, bufferSize, &mBuffers[i]);
    
    // 4. [极其重要] 预热：在开播前，手动触发一次回调，或者手动把第一批数据塞进这 3 个 buffer 
    MyAudioQueueOutputCallback((__bridge void *)(self), mAudioQueue, mBuffers[i]);
}

// 5. 调整音量（可选，1.0 代表原音量）
AudioQueueSetParameter(mAudioQueue, kAudioQueueParam_Volume, 1.0);

// 6. 拉闸，正式开播！
AudioQueueStart(mAudioQueue, NULL);
```

### 4. 常见避坑与高级技巧

#### ① 线程安全与卡顿问题

`AudioQueueNewOutput` 触发的回调函数 `MyAudioQueueOutputCallback` 运行在 **Apple 系统底层专有的音频线程**中。

- **绝对不要**在这个回调函数里做任何耗时的操作（比如直接在里面调用网络请求、或者直接调用复杂的 FFmpeg 解码命令）。
- **正确做法**：应该有一个独立的“解码线程”源源不断地把 FFmpeg 解码重采样后的 PCM 丢进一个多线程安全的 FIFO 队列（或环形缓冲区/RingBuffer）里。回调函数只负责用极快的速度去这个环形缓冲区里 `memcpy` 取数据。如果取不到，说明解码速度跟不上了，声音就会发生“断音/丢包杂音”。

#### ② 销毁的正确姿势

当切换歌曲或关闭播放器时，销毁资源需要严格按部就班：

```objective-c
// 1. 停止队列（同步停止，会等待当前 Buffer 播放完）
AudioQueueStop(mAudioQueue, YES);

// 2. 销毁队列（函数内部会自动释放通过 AudioQueueAllocateBuffer 分配的那 3 个 buffer）
AudioQueueDispose(mAudioQueue, YES);
mAudioQueue = NULL;
```
