# avcodec_find_decoder

在 FFmpeg 的完整处理流水线中，**`avcodec_find_decoder`** 是你进入“解码世界”的第一个路口。

它的核心任务非常纯粹：**根据你给出的解码器 ID（Codec ID），在 FFmpeg 庞大的解码器“武器库”中，精准地帮你把那个负责具体解码的工具人（`AVCodec` 结构体）给揪出来。**

### 1. 函数原型

FFmpeg 提供了两个用于寻找解码器的函数，它们的底层逻辑一致，但查找的“依据”不同：

#### ① 按 ID 查找（最常用）

```c
const AVCodec *avcodec_find_decoder(enum AVCodecID id);
```

- **参数**：一个枚举值（如 `AV_CODEC_ID_H264`、`AV_CODEC_ID_HEVC`、`AV_CODEC_ID_AAC` 等）。
- **返回值**：找到的解码器指针（`const AVCodec *`）。如果不支持该格式，返回 `NULL`。

#### ② 按名称查找（用于指定特定软硬解）

```c
const AVCodec *avcodec_find_decoder_by_name(const char *name);
```

- **参数**：字符串名称（如 `"h264"`、`"h264_qsv"` 意为英特尔硬件加速、`"h264_mediacodec"` 意为安卓硬解）。

### 2. 它在经典调用链中的位置

我们在初始化 `AVCodecContext` 时，它是第一步：

```c
AVStream *stream = pFormatCtx->streams[video_idx];

// 1. 看看这个流是什么格式，然后去找对应的解码器 ──► 【avcodec_find_decoder】
const AVCodec *pCodec = avcodec_find_decoder(stream->codecpar->codec_id);

// 2. 拿着解码器去分配上下文
AVCodecContext *pCodecCtx = avcodec_alloc_context3(pCodec);

// 3. 把流里的参数复制给上下文
avcodec_parameters_to_context(pCodecCtx, stream->codecpar);

// 4. 正式打开解码器
avcodec_open2(pCodecCtx, pCodec, NULL);
```

### 3. 它背后的工作原理

FFmpeg 内部维护着一个**全局的解码器链表**。

当你调用 `avcodec_find_decoder(AV_CODEC_ID_H264)` 时，它会在链表中从头到尾进行遍历，匹配每一个解码器的 `id` 属性。一旦匹配成功，就返回这个解码器的静态结构体地址。

> **💡 时代变了（关于注册的旧历史）：**
>
> 如果你在看 2018 年以前的老教程，会发现调用这个函数前必须先写一句 `av_register_all()` 或 `avcodec_register_all()`。
>
> **请注意：从 FFmpeg 4.0 开始，这些注册函数已被彻底废弃！** 现在的 FFmpeg 内部会自动维护这个链表，你直接调用 `avcodec_find_decoder` 即可。

### 4. 典型代码示例与安全检查

这个函数的返回值**必须进行非空检查**。因为很多轻量化的 FFmpeg 编译版本（如某些精简版动态库）为了裁剪体积，会把不常用的格式（如一些老旧的音频格式、某些商业版权限制的格式）直接删掉。

```c
// 假设已通过 avformat_find_stream_info 获取到了流信息
AVStream *video_stream = pFormatCtx->streams[video_stream_index];

// 寻找解码器
const AVCodec *pCodec = avcodec_find_decoder(video_stream->codecpar->codec_id);

if (!pCodec) {
    fprintf(stderr, "错误：当前 FFmpeg 库不支持该视频格式的解码器 (Codec ID: %d)!\n", 
            video_stream->codecpar->codec_id);
    return -1;
}

// 打印一下找到的解码器叫什么名字
printf("成功找到解码器：%s (%s)\n", pCodec->name, pCodec->long_name);
// 比如会输出：成功找到解码器：h264 (H.264 / AVC / MPEG-4 AVC / MPEG-4 part 10)
```

### 5. 进阶技巧：如何指定“硬解码器”？

`avcodec_find_decoder` 默认寻找的是 **最通用的通用解码器（通常是 CPU 软解，如 libx264 对应的内部实现）**。

如果你在做高性能开发（比如 4K/8K 视频播放、多路高并发视频分析），想要榨干显卡的性能，就需要换用 **`avcodec_find_decoder_by_name`**。

```c
// 软解（默认）：使用 CPU 解码
const AVCodec *softCodec = avcodec_find_decoder(AV_CODEC_ID_H264);

// 硬解（NVIDIA 显卡 CUVID 加速，需要显卡驱动和编译支持）
const AVCodec *cudaCodec = avcodec_find_decoder_by_name("h264_cuvid");

// 硬解（Intel 显卡 QuickSync 加速）
const AVCodec *qsvCodec = avcodec_find_decoder_by_name("h264_qsv");

if (cudaCodec) {
    printf("可使用 NVIDIA 硬件加速解码！\n");
}
```

### 总结

`avcodec_find_decoder` 就像是去仓库里拿工具。你告诉它你需要修理什么样的螺丝（`CodecID`），它就帮你把对应的扳手（`AVCodec`）递给你。拿到扳手后，你才能把它组装到你的工作台（`AVCodecContext`）上开始干活。



# avcodec_alloc_context3

在 FFmpeg 中，**`avcodec_alloc_context3`** 是为你即将进行的“编码”或“解码”工作**搭建舞台、分配办公场所**的函数。

它的核心任务非常纯粹：**在堆（Heap）上动态分配一个 `AVCodecContext`（解码器/编码器上下文）结构体的内存，并将其中的各项参数初始化为默认值。**

### 1. 函数原型

```c
AVCodecContext *avcodec_alloc_context3(const AVCodec *codec);
```

- **参数 `codec`**：

  传入你之前通过 `avcodec_find_decoder` 或 `avcodec_find_encoder` 找到的解码器或编码器指针。

  - *可以传 `NULL` 吗？* ── **可以。** 如果传 `NULL`，它会分配一个通用的、未绑定任何特定具体编解码器的上下文，后续你需要手动指定。但通常建议直接传入对应的 `AVCodec` 指针。

- **返回值**：

  成功时返回指向新分配的 `AVCodecContext` 的指针；如果内存不足，返回 `NULL`。

### 2. 为什么要用这个函数，而不是直接定义结构体？

在 C/C++ 开发中，我们经常习惯直接定义结构体（如 `AVCodecContext ctx;`）。但在 FFmpeg 中，**这是绝对禁止的**，原因有两点：

1. **版本向前兼容（二进制安全）**：`AVCodecContext` 是一个极度庞大的结构体。随着 FFmpeg 的升级，官方经常会在结构体的**末尾**添加新的成员变量（比如支持新的硬件加速特性、新的色彩空间）。如果你在自己的代码里直接定义或者用 `malloc` 分配，一旦动态库升级，结构体的大小就变了，你的程序就会直接内存越界崩溃。
2. **默认值的初始化**：FFmpeg 的参数极其复杂（多达上百个）。`avcodec_alloc_context3` 内部会调用特定的初始化函数，确保所有控制开关、指针、缓冲区长度都被安全地赋上了系统默认值，避免出现野指针。

### 3. 在解码与编码流程中的不同用法

虽然调用的函数是一样的，但在**解码**和**编码**的管线里，由于数据来源不同，这个函数之后的逻辑完全相反：

#### 场景 A：视频解码（解压文件播放）

在解码时，视频的分辨率、帧率、音频的采样率都是**文件本身决定**的。所以分配完上下文后，我们需要从文件流里把参数“拷贝”过来：

```c
// 1. 找到解码器
const AVCodec *pCodec = avcodec_find_decoder(pStream->codecpar->codec_id);

// 2. 为上下文分配内存（绑定解码器）
AVCodecContext *pCodecCtx = avcodec_alloc_context3(pCodec);
if (!pCodecCtx) return -1;

// 3. 极其重要：从输入流中拷贝媒体参数（宽高、声道等）到上下文中
avcodec_parameters_to_context(pCodecCtx, pStream->codecpar);

// 4. 正式打开解码器
avcodec_open2(pCodecCtx, pCodec, NULL);
```

#### 场景 B：视频编码（压缩数据录制）

在编码时，上下文里的参数是**由你（开发者）决定**的。你必须手动一行行地告诉编码器你想压缩成多大的视频：

```c
// 1. 找到 H.264 编码器
const AVCodec *pCodec = avcodec_find_encoder(AV_CODEC_ID_H264);

// 2. 为上下文分配内存
AVCodecContext *pCodecCtx = avcodec_alloc_context3(pCodec);

// 3. 手动填充你想要的编码参数
pCodecCtx->width = 1920;                  // 目标宽度
pCodecCtx->height = 1080;                 // 目标高度
pCodecCtx->bit_rate = 4000000;            // 目标码率 4Mbps
pCodecCtx->time_base = (AVRational){1, 25}; // 帧率 25 fps
pCodecCtx->pix_fmt = AV_PIX_FMT_YUV420P;   // 编码器接收的像素格式

// 4. 正式打开编码器
avcodec_open2(pCodecCtx, pCodec, NULL);
```

### 4. 为什么函数名后面有个数字 “3” ？（历史小八卦）

如果你看 FFmpeg 早期的代码，会发现有 `avcodec_alloc_context()` 甚至 `avcodec_alloc_context2()`。

- 最早的 `alloc_context` 不需要传任何参数。
- 后来发现，如果不把 `AVCodec` 传进去，系统就无法在分配内存的第一时间去初始化那些“专属于该编解码器”的特定私有参数（比如针对 H.264 的特殊优化配置）。
- 于是官方推出了带 `3` 的版本，把 `AVCodec` 作为参数强制约束。如今，老版本的函数都已经被彻底废弃。

### 5. 内存释放的安全警示

有分配就必须有释放。只要你成功调用了 `avcodec_alloc_context3`，在程序退出或关闭流时，必须使用配套的释放函数：

```c
// 销毁上下文，并自动将指针置为 NULL，防止野指针
avcodec_free_context(&pCodecCtx);
```

> **注意**：千万不要用 C 语言自带的 `free(pCodecCtx)`。因为 `AVCodecContext` 内部还挂载着很多其他的子内存块和缓冲区（比如多线程解码的内部线程队列），直接 `free` 会导致严重的内部内存泄漏。

### 总结

`avcodec_alloc_context3` 就是在工地上为你盖起一间名为 `AVCodecContext` 的“核心加工厂”。厂子盖好后，你要么把图纸塞给它（解码时拷贝流参数），要么自己手动往里配设备（编码时手工配参数），最后拉闸开工（`avcodec_open2`）。



# CVPixelBufferRef

突然聊到 **`CVPixelBufferRef`**，我们的视线就需要从纯粹的开源跨平台 FFmpeg，暂时移动到 Apple 的生态圈（iOS / macOS）中了。

在 Apple 的核心视频框架（Core Video）中，`CVPixelBufferRef` 是绝对的“一号主角”。简单来说，它就是 **Apple 官方定义的一帧原始视频画面（像素缓冲区）的内存句柄**。

### 1. 它到底是什么？跟 FFmpeg 的 `AVFrame` 有什么关系？

你可以把它直接类比为 **Apple 版本的 `AVFrame`**。它们存的都是没有压缩的原始像素数据（如 NV12、YUV420P、RGBA 等）。

但它们有一个巨大的底层区别：

- **`AVFrame`**：通常是纯 **CPU 内存**（内存里的一个数组）。
- **`CVPixelBufferRef`**：它是一个极其聪明的抽象。它既可以代表普通的 CPU 内存，也可以直接代表 **GPU 显存（纹理）**。更厉害的是，它支持 **零拷贝（Zero-Copy）**。

在 iOS/macOS 上，不管是摄像头的采集输出（AVFoundation）、硬解码器的输出（VideoToolbox），还是屏幕的渲染（Metal / OpenGL ES），大家都统一使用 `CVPixelBufferRef` 作为普通话进行交流。

### 2. 它的内存结构：平面（Planar）与跨度（BytesPerRow）

和 `AVFrame` 一样，`CVPixelBufferRef` 也要处理像素的排列问题。我们以 iOS 上最常用的视频格式 **NV12** 为例：

```
[ CVPixelBufferRef ]
       │
       ├─► Plane 0: Y (亮度平面) ──► 内存地址: CVPixelBufferGetBaseAddressOfPlane(p, 0)
       │                           每行步长: CVPixelBufferGetBytesPerRowOfPlane(p, 0)
       │
       └─► Plane 1: UV (色度平面) ──► 内存地址: CVPixelBufferGetBaseAddressOfPlane(p, 1)
                                   每行步长: CVPixelBufferGetBytesPerRowOfPlane(p, 1)
```

#### ⚠️ 避坑大彩蛋：`BytesPerRow` 并不等于 `Width`

这是初学者 99% 会踩的系统级大坑。

当你通过 `CVPixelBufferGetWidth` 拿到视频宽度是 `1080` 时，你通过 `CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 0)` 拿到的步长可能是 `1088` 甚至 `1120`。

这是因为 Apple 底层为了让硬件（CPU/GPU）读取内存时实现字节对齐（比如 64 字节对齐）以极大提升运行速度，会在每行画面的末尾塞入一些毫无意义的空白占位符（Padding）。你在提取像素、做人脸识别或者转成 FFmpeg 数据时，**必须按照 `BytesPerRow` 逐行循环拷贝**，绝对不能用 `width * height` 一口气打包带走！

### 3. 核心生命周期与操作代码

因为 `CVPixelBufferRef` 是基于 C 语言的 Core Foundation 框架（CF），它不受 Objective-C / Swift 的自动引用计数（ARC）管辖。你必须手动管理它的生死：

#### 🛠️ 如何用 CPU 读写 `CVPixelBufferRef` 内部的像素？

如果你想直接修改或读取里面的画面，必须先对其进行**内存锁定**：

```objective-c
// 1. 增加引用计数（如果需要持有它）
CVPixelBufferRetain(pixelBuffer);

// 2. 访问前：锁定基地址，告诉系统“我要用CPU读写这段内存了，GPU先别动”
// kCVPixelBufferLock_ReadOnly 代表只读，如果是读写可以传 0
CVPixelBufferLockBaseAddress(pixelBuffer, kCVPixelBufferLock_ReadOnly);

// 3. 获取基本信息
size_t width = CVPixelBufferGetWidth(pixelBuffer);
size_t height = CVPixelBufferGetHeight(pixelBuffer);

// 4. 获取像素格式（比如 '420v' 代表 NV12, 'BGRA' 代表 RGBA）
OSType pixelFormat = CVPixelBufferGetPixelFormatType(pixelBuffer);

// 5. 获取具体的 Y 平面内存指针
uint8_t *y_data = (uint8_t *)CVPixelBufferGetBaseAddressOfPlane(pixelBuffer, 0);
size_t y_stride = CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 0);

// ... 在这里做你的图像处理（比如拷贝给 FFmpeg 的 AVFrame） ...

// 6. 访问后：必须解锁！否则这块内存会被卡死，引发严重的内存或画面渲染断流
CVPixelBufferUnlockBaseAddress(pixelBuffer, kCVPixelBufferLock_ReadOnly);

// 7. 释放引用计数（不用时必须释放，否则直接内存泄漏）
CVPixelBufferRelease(pixelBuffer);
```

### 4. 它与 FFmpeg 的梦幻联动（硬解结合）

在 iOS/macOS 上做高性能开发时，我们经常把 FFmpeg 和 `CVPixelBuffer` 结合使用。

**经典场景：FFmpeg 硬解码（VideoToolbox）**

当你开启了 FFmpeg 的 `h264_mediacodec` 或 `h264_videotoolbox` 硬件加速解码后，FFmpeg 解码出来的 `AVFrame` 内部，其实并没有真正的 YUV 字节数组。它的 `frame->data[3]`（或者通过特定 API）里，实际藏着的正是 Apple 原生的 **`CVPixelBufferRef`**！

通过把这个 `CVPixelBufferRef` 直接扔给 iOS 的 `AVSampleBufferDisplayLayer` 或者转成 Metal 纹理，你可以实现**完全不经过 CPU、纯 GPU 级别的超高性能级视频渲染**。

### 总结对比

| **特性**     | **FFmpeg AVFrame**                     | **Apple CVPixelBufferRef**                   |
| ------------ | -------------------------------------- | -------------------------------------------- |
| **出身**     | 开源跨平台的多媒体框架                 | Apple 官方 Core Video 视频基石               |
| **内存位置** | 默认 CPU 内存（由 `AVBufferRef` 管理） | 可在 CPU，也可在显存（和多媒体硬件彻底打通） |
| **管理机制** | 内部引用计数（`av_frame_unref`）       | 经典的 C 语言 `Retain/Release` 机制          |



# CVPixelBufferCreate

在 Apple 的 Core Video 框架中，**`CVPixelBufferCreate`** 是专门用来在堆上开辟一块全新的原始像素缓冲区（也就是创建一块干净的画布）的底库级函数。

如果你正在开发摄像头采集、滤镜处理、或者将 FFmpeg 解码出来的原始 YUV/RGB 数据打包塞给 iOS/macOS 的原生硬编码器（VideoToolbox），你都必须通过这个函数来亲手初始化一块 `CVPixelBufferRef`。

### 1. 函数原型

C

```
CVReturn CVPixelBufferCreate(
    CFAllocatorRef _Nullable allocator,
    size_t width,
    size_t height,
    OSType pixelFormatType,
    CFDictionaryRef _Nullable pixelBufferAttributes,
    CVPixelBufferRef  _Nullable * _Nonnull pixelBufferOut
);
```

#### 参数深度拆解：

1. **`allocator`**: 内存分配器。通常传入 `kCFAllocatorDefault`（或 `NULL`），表示使用系统默认的内存分配机制。
2. **`width` / `height`**: 你想要创建的画面**分辨率宽高**（像素单位）。
3. **`pixelFormatType`**: **像素格式**。传入一个由四个字符组成的整型四字码（FourCC）。iOS/macOS 最常用的有：
   - `kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange` (即 `'420v'`，最常用的 **NV12** 视频范围格式)
   - `kCVPixelFormatType_32BGRA` (即 `'BGRA'`，常用于屏幕渲染、UI 交互)
4. **`pixelBufferAttributes`**: 一个字典，用来指定这块缓冲区的**特殊物理属性**（比如：是否需要支持 OpenGL/Metal 纹理兼容，内存是否要强制对齐等）。如果不要特殊处理，传 `NULL`。
5. **`pixelBufferOut`**: 输出参数。传入一个 `CVPixelBufferRef` 的指针地址，创建成功后，新缓冲区的句柄会写入这里。

- **返回值 (`CVReturn`)**: 如果成功返回 `kCVReturnSuccess` (值为 `0`)，失败则返回相应的错误码。

### 2. 核心实战代码：如何创建并往里灌数据？

在实际开发中（比如将 FFmpeg 的 `AVFrame` 数据拷贝进 `CVPixelBuffer` 以便送去 Apple 的硬编码器），最经典的用法如下：

Objective-C

```
CVPixelBufferRef pixelBuffer = NULL;

// 1. 定义像素缓冲区的属性（为了让它能完美和 iOS 的 GPU 渲染及硬编码兼容）
NSDictionary *attributes = @{
    (__bridge NSString *)kCVPixelBufferIOSurfacePropertiesKey: @{}, // 启用 IOSurface 以实现跨进程/GPU零拷贝
    (__bridge NSString *)kCVPixelBufferMetalCompatibilityKey: @YES    // 允许 Metal 直接访问
};

// 2. 创建一个 1920x1080 的 NV12 (420v) 画布
CVReturn status = CVPixelBufferCreate(kCFAllocatorDefault,
                                      1920,
                                      1080,
                                      kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange,
                                      (__bridge CFDictionaryRef)attributes,
                                      &pixelBuffer);

if (status != kCVReturnSuccess || pixelBuffer == NULL) {
    printf("创建 CVPixelBuffer 失败，错误码: %d\n", status);
    return;
}

// 3. 锁定内存，准备通过 CPU 写入数据
CVPixelBufferLockBaseAddress(pixelBuffer, 0);

// 4. 获取刚刚开辟的内存指针（以 NV12 为例）
uint8_t *y_dest = (uint8_t *)CVPixelBufferGetBaseAddressOfPlane(pixelBuffer, 0);
size_t y_stride = CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 0); // 注意对齐步长

uint8_t *uv_dest = (uint8_t *)CVPixelBufferGetBaseAddressOfPlane(pixelBuffer, 1);
size_t uv_stride = CVPixelBufferGetBytesPerRowOfPlane(pixelBuffer, 1);

// [核心步骤]：在这里使用 memcpy，将你的原始数据（如 FFmpeg 的 AVFrame->data）
// 依据 y_stride 和 uv_stride 逐行拷贝到 y_dest 和 uv_dest 中。

// 5. 写入完毕，立刻解锁
CVPixelBufferUnlockBaseAddress(pixelBuffer, 0);

// ......
// 拿着这个打包好数据的 pixelBuffer 送去给 VideoToolbox 编码，或者丢给渲染层
// ......

// 6. 最后的谢幕：用完后必须手动释放，否则内存瞬间暴涨导致崩溃 (OOM)
CVPixelBufferRelease(pixelBuffer);
```

### 3. 进阶避坑与性能优化指南

#### ① `CVPixelBufferCreate` 还是 `CVPixelBufferCreateWithBytes`？

如果你手里**已经有一块**用 `malloc` 分配好的、装满像素的底层内存，你可能会想用 `CVPixelBufferCreateWithBytes`（包装已有内存）。

**⚠️ 强烈建议不要这样做！**

因为通过 `CVPixelBufferCreate` 由系统直接分配的内存，会自动被标记为支持 iOS 底层的 `IOSurface`。这意味着它在硬件层面是高度优化的，可以实现 **CPU 到 GPU 的零拷贝快道**。如果你用自己 `malloc` 的内存去包装，往往无法直接送入硬件编码器，甚至在渲染时引发强制性的内存拷贝，导致 CPU 占用率飙升。

#### ② 跨度（Stride）填充陷阱

正如此前提到的，当系统为你通过 `CVPixelBufferCreate` 创建完一块画布后，由于内存对齐的原因，系统分配给你的实际每行宽度（`BytesPerRow`）**往往比你申请的 `width` 大**。因此往里写数据时，千万不能用一个大 `memcpy` 把一整块全吞下去，一定要写一个 `for` 循环，按行安全对接。

#### ③ 属性字典里的魔鬼细节

如果你创建的 `CVPixelBuffer` 是准备用来和 **OpenGL ES / Metal / WebRTC** 梦幻联动的，在 `pixelBufferAttributes` 里一定要加上对应的键（如 `kCVPixelBufferMetalCompatibilityKey`）。否则，当你后续尝试将这块内存转化为 GPU 纹理时，系统会无情地给你报一个失败。

### 总结

调用 `CVPixelBufferCreate` 就像是向 Apple 的内存大管家申请了一张“带有苹果硬件通关绿卡”的空白白纸。你严格按照它的表格规格（`BytesPerRow`）把画面像素画在上面，然后这张纸就可以在 Apple 系统的摄像头、编码器、显卡之间一路绿灯地高效流转了。



# sws_getCachedContext



在刚刚讲解 `SwsContext` 时，我特别强调过：**绝对不要把 `sws_getContext` 放在视频读取的循环里**，因为每次创建上下文都会引发大量的矩阵计算和内存分配，极其消耗性能。

但是，在实际开发中，我们经常会遇到**动态流**。比如播放一个网络 HLS 流、M3U8 直播或者切换清晰度时，视频的分辨率（从 720P 突变成 1080P）或者像素格式可能会在播放途中**突然发生改变**。

这时候，**`sws_getCachedContext`** 就是为了优雅、高效地解决“动态参数改变”而诞生的。

### 1. 函数原型



```c
struct SwsContext *sws_getCachedContext(
    struct SwsContext *context,              // 输入：旧的上下文指针（可以为 NULL）
    int srcW, int srcH, enum AVPixelFormat srcFormat, // 输入：新一帧画面的宽、高、格式
    int dstW, int dstH, enum AVPixelFormat dstFormat, // 输出：你期望目标的宽、高、格式
    int flags,                               // 缩放算法标签
    SwsFilter *srcFilter, SwsFilter *dstFilter,
    const double *param
);
```

### 2. 它有多聪明？（核心复用机制）

这个函数之所以叫 “Cached”（带缓存的），是因为它内部自带了一套**智能检测和复用逻辑**。

当你把**旧的上下文**和**新一帧的参数**传给它时，它会进行以下判断：

1. **参数未变**：如果检查到新的 `srcW/srcH/srcFormat` 以及目标参数，与旧的 `context` 内部记录的参数**完全一致**。那它什么都不做，直接把传入的 `context` **原封不动地返回**给你。这几乎没有任何性能开销。
2. **参数变了**：如果发现分辨率变了（比如从 $1280 \times 720$ 变成了 $1920 \times 1080$），它会在内部**先安全地销毁（Free）旧的上下文，然后根据新参数重新创建（Alloc）一个全新的上下文**，再返回给你。

### 3. 实战代码：它在播放循环中的标准姿势

有了这个函数，你就再也不用在循环里写一堆 `if (width != old_width)` 这种繁琐的判断逻辑了。直接闭着眼睛调用它，让它帮你托管。

C

```c
// 1. 在循环外部，初始化一个空的上下文指针
struct SwsContext *sws_ctx = NULL;

// 目标输出参数（假设固定转为 1280x720 RGBA 用于显示）
int dst_w = 1280;
int dst_h = 720;
enum AVPixelFormat dst_fmt = AV_PIX_FMT_RGBA;

// 2. 视频解码主循环
while (av_read_frame(fmt_ctx, pkt) >= 0) {
    // ... 经历 avcodec_send_packet 和 avcodec_receive_frame ...
    // 假设此时成功解码出了一帧：pFrame
    
    // 3. 核心魔术步骤：检查并获取/复用上下文
    // 如果视频没变，这行代码极快；如果视频中途变了，它会自动无缝重建
    sws_ctx = sws_getCachedContext(
        sws_ctx,             // 传入旧的指针
        pFrame->width, pFrame->height, pFrame->format, // 当前帧的实际参数
        dst_w, dst_h, dst_fmt,                         // 目标输出参数
        SWS_BILINEAR, NULL, NULL, NULL
    );
    
    if (!sws_ctx) {
        printf("无法创建或更新 SwsContext\n");
        break;
    }
    
    // 4. 放心大胆地进行像素转换
    sws_scale(sws_ctx, pFrame->data, pFrame->linesize, 0, pFrame->height, 
              outputFrame->data, outputFrame->linesize);
              
    // ... 去渲染或者处理 outputFrame ...
}

// 5. 退出循环后，彻底打扫战场
if (sws_ctx) {
    sws_freeContext(sws_ctx);
}
```

### 4. 避坑指南：必须了解的内部细节

1. **别忘了接收返回值**：

   必须写成 `sws_ctx = sws_getCachedContext(sws_ctx, ...)`。因为当参数改变时，函数内部会把旧的内存释放掉，并产生一个**新地址**。如果你不把新地址赋值给你的指针变量，你的变量就会变成一个非法的“野指针”，下次循环直接引发程序崩溃（Segmentation Fault）。

2. **目标缓冲区的动态联动**：

   如果你的**输出目标参数**（`dstW/dstH`）也是随着输入动态变化的（比如保持原图比例缩放），一旦 `sws_getCachedContext` 触发了重建，你后面用来承载数据的那个目标 `AVFrame`（代码中的 `outputFrame`）也**必须跟着重新申请内存（`av_frame_unref` 后重新 `av_frame_get_buffer`）**。否则，小尺寸的上下文往旧的大尺寸 Buffer 里写数据没事，但如果是小尺寸突变到大尺寸，会导致内存越界写入。

### 总结

在编写健壮的、商业级的播放器或转码引擎时，**`sws_getCachedContext` 几乎是行业标准的首选写法**。它不仅精简了你的代码结构，还自动帮你把“格式突变”这种异常流的安全边界给守住了。
