# avformat_open_input



在 FFmpeg 的开发世界里，`avformat_open_input` 是你与多媒体文件“初次见面”的地方。它的主要任务是**打开输入流**并**读取文件头信息**，但它并不会去处理具体的音视频数据。

你可以把它想象成：你拿到了一本书，这个函数帮你**打开封面**，看了看**目录**（容器格式、封装信息），但还没开始读正文。

### 1. 函数原型

```c
int avformat_open_input(AVFormatContext **ps, const char *url, 
                        const AVInputFormat *fmt, AVDictionary **options);
```

### 2. 参数深度解析

- **`AVFormatContext ps`**:

  这是最重要的参数。它是 FFmpeg 的“总管”，包含了文件的封装格式、流信息等。

  - 如果你传入 `NULL`，函数内部会自动帮你 `avformat_alloc_context()`。
  - 如果你已经手动分配了空间，函数会直接使用它。

- **`const char \*url`**:

  要打开的文件路径。它可以是本地文件（`C:/video.mp4`），也可以是网络流（`rtmp://...` 或 `http://...`）。

- **`const AVInputFormat \*fmt`**:

  强制指定的输入格式。通常传 `NULL`，让 FFmpeg 自动探测（Probe）文件的格式。

- **`AVDictionary options`**:

  额外的配置参数。比如设置 RTSP 的传输协议（TCP/UDP）或者超时时间。

### 3. 它背后做了什么？（工作流程）

当你调用这个函数时，FFmpeg 内部经历了一系列复杂的“侦查”工作：

1. **分配上下文**：确保 `AVFormatContext` 准备就绪。
2. **探测协议**：根据 URL 的前缀（如 `http://`）找到对应的 `URLProtocol`。
3. **打开 I/O**：调用 `avio_open2` 打开底层的比特流。
4. **探测封装格式 (Probe)**：
   - 如果用户没指定 `fmt`，FFmpeg 会读取文件的前几个字节（通常是几 KB）。
   - 通过这些特征字节（如 MP4 的 `ftyp`，FLV 的 `FLV` 标志）来判断这到底是个什么文件。
5. **读取基本元数据**：填充 `AVFormatContext` 里的基本信息，比如文件时长、流的数量等。

### 4. 典型用法示例

```c
AVFormatContext *pFormatCtx = NULL;
const char *url = "test.mp4";

// 打开文件
int ret = avformat_open_input(&pFormatCtx, url, NULL, NULL);

if (ret < 0) {
    char errbuf[1024];
    av_strerror(ret, errbuf, sizeof(errbuf));
    printf("无法打开输入文件: %s\n", errbuf);
    return -1;
}

// 接下来通常配合 avformat_find_stream_info 使用，以获取更详尽的流信息
```

### 5. 易错点与注意事项

- **返回值检查**：一定要检查返回值。FFmpeg 的函数成功通常返回 `0`，失败返回负数（错误码）。
- **资源释放**：只要 `avformat_open_input` 执行成功，后续必须调用 `avformat_close_input(&ps)` 来释放资源，否则会造成内存泄漏。
- **它并不获取全部信息**：`avformat_open_input` 只是“打开”了文件。有些格式（如 H.264 原始流）在文件头里没写帧率等信息。这时你必须紧接着调用 `avformat_find_stream_info()`，让 FFmpeg 试着解码几帧来“猜”出完整的流信息。

### 总结表格

| **特性**         | **说明**                                                 |
| ---------------- | -------------------------------------------------------- |
| **主要功能**     | 打开多媒体文件/流，探测格式，读取文件头                  |
| **是否解码**     | **不解码**，只负责解封装（Demux）的准备工作              |
| **依赖**         | 需要先调用 `avdevice_register_all()` (可选) 或网络初始化 |
| **对应释放函数** | `avformat_close_input`                                   |



# avformat_find_stream_info

如果在 `avformat_open_input` 之后，FFmpeg 开发中有一个函数堪称“幕后劳模”，那绝对是 **`avformat_find_stream_info`**。

前面提到，`avformat_open_input` 只是打开了文件的大门，读了读“书名”和“目录”（文件头）。但是，很多多媒体文件（比如原始的 H.264/H.265 码流、AAC 编码的音频，或者某些没写完整的 MP4 文件）在文件头里**根本没有帧率、分辨率、时长或者像素格式**等关键信息。

`avformat_find_stream_info` 的任务就是：**通过“试读”一部分媒体数据并进行试解码，来彻底摸清文件里所有音视频流的详细底细。**

### 1. 函数原型

C

```c
int avformat_find_stream_info(AVFormatContext *ic, AVDictionary **options);
```

### 2. 它在调用链中的位置

在标准的 FFmpeg 初始化流程中，它的位置是承上启下的：

```
avformat_open_input() 
       ↓ （此时只有基础的文件封装信息）
avformat_find_stream_info() 
       ↓ （此时有了完美的流信息：分辨率、帧率、解码器参数）
// 接下来才可以去匹配音视频流、打开具体的解码器...
```

### 3. 它背后的工作原理（为什么它很慢？）

这个函数并不是简单地读几个字节，它是会**动真格**的：

1. **读取数据包**：它会在内部调用 `av_read_frame()` 读取一部分音视频的原始数据包（Packets）。
2. **送入探测解码器**：它内部甚至会启动一个临时的解码器，把这些数据包真的解出来几帧（Frames）。
3. **计算与推理**：
   - 比如它连读了 10 帧视频，发现它们之间的时间戳（PTS/DTS）差值很固定，它就能**推算出帧率**。
   - 通过解码前几帧，它能百分之百确定视频的**分辨率（Width/Height）\**和\**像素格式（如 YUV420P）**。
4. **达到限制后退出**：当摸清了所有流的信息，或者读取的数据量/时间达到了设定的上限，它就会停止并返回。

### 4. 关键内部控制参数（性能优化的关键）

因为这个函数要读数据甚至试解码，所以它**必然会消耗时间并产生网络流量**（如果是网络流）。

为了防止它在遇到坏片或极慢的网络流时无限卡死，`AVFormatContext` 中有几个关键的隐藏参数在控制它的行为：

- **`probesize`**（默认 5,000,000 字节，约 5MB）：允许为了探测流信息而读取的最大字节数。
- **`max_analyze_duration`**（默认 5,000,000 微秒，即 5 秒）：允许为了分析流信息而消耗的最大媒体时长。

#### 🚀 优化小技巧（如果你在做直播或追求秒开）：

如果你在播放**直播流（如 RTMP/RTSP）**，5 秒的分析时间会导致严重的开播延迟。你可以手动把这两个值调小，拿“牺牲部分不常见格式的准确性”来换取“极速开播”：

C

```c
AVFormatContext *pFormatCtx = avformat_alloc_context();

// 在 avformat_open_input 之前或之后（find_stream_info 之前）设置
pFormatCtx->probesize = 500000;        // 缩小到 500KB
pFormatCtx->max_analyze_duration = 1000000; // 缩小到 1 秒

int ret = avformat_find_stream_info(pFormatCtx, NULL);
```

### 5. 典型代码示例

C

```c
// 假设 pFormatCtx 已经成功通过 avformat_open_input 打开

// 获取详尽的流信息
int ret = avformat_find_stream_info(pFormatCtx, NULL);
if (ret < 0) {
    char errbuf[1024];
    av_strerror(ret, errbuf, sizeof(errbuf));
    printf("无法获取流信息: %s\n", errbuf);
    return -1;
}

// 执行成功后，你现在可以放心大胆地读取这些核心信息了：
for (unsigned int i = 0; i < pFormatCtx->nb_streams; i++) {
    AVStream *stream = pFormatCtx->streams[i];
    AVCodecParameters *codec_par = stream->codecpar;
    
    if (codec_par->codec_type == AVMEDIA_TYPE_VIDEO) {
        printf("视频分辨率: %d x %d\n", codec_par->width, codec_par->height);
        printf("视频帧率: %.2f\n", av_q2d(stream->avg_frame_rate));
    } else if (codec_par->codec_type == AVMEDIA_TYPE_AUDIO) {
        printf("音频采样率: %d Hz\n", codec_par->sample_rate);
        printf("音频通道数: %d\n", codec_par->ch_layout.nb_channels);
    }
}
```

### 6. 避坑与注意事项

1. **网络流卡死问题**：如果网络极其糟糕，或者 HTTPS 链接突然中断，这个函数可能会阻塞在里面。建议配合 `AVFormatContext` 的 `interrupt_callback`（中断回调机制）来实现超时强退。
2. **`options` 参数的作用**：它的第二个参数 `AVDictionary options` 是一个数组，可以针对文件里的每一个流传入不同的解码参数（很少用到，一般传 `NULL`）。
3. **不能省略它吗？**：对于信息写得很完美的 MP4、MKV，不调用它有时也能拿到分辨率。但为了程序的健壮性（兼容各种奇葩文件、TS 流、直播流），**强烈建议不要省略这一步**。

### 总结对比

| **函数**     | **avformat_open_input**         | **avformat_find_stream_info**       |
| ------------ | ------------------------------- | ----------------------------------- |
| **关注点**   | 文件的**容器/封装格式**（外壳） | 容器内的**每一个音视频流**（内核）  |
| **耗时**     | 极低（只读头部）                | 较高（涉及读数据包、试解码）        |
| **主要产出** | `AVFormatContext` 的基本骨架    | `AVStream->codecpar` 的完整细节参数 |

在配合你之前提到的 HTTPS + Token 的场景下，这个函数会利用 `open_input` 建立好的加密通道继续向后读数据。



# 扩展：URL需要token等认证信息时

当视频资源需要 Token、Cookie 或特定的身份验证（如 OAuth 或自定义 Header）时，你不能直接把 URL 传给 `avformat_open_input`。

你需要利用 FFmpeg 的 **`AVDictionary`** 系统，将验证信息注入到 HTTP 请求头中。

### 1. 通过 `headers` 参数注入 Token

这是最通用的方法。你可以手动构建 HTTP 请求头字符串，包括 `Authorization`、`Token` 或 `Cookie`。

**代码示例：**

```c
AVFormatContext *pFormatCtx = avformat_alloc_context();
AVDictionary *options = NULL;

// 注意：每一个 Header 后面必须跟上 \r\n，即使是最后一个
// 下面演示了同时加入 Authorization Token 和 一个自定义的 X-Access-Token
const char *my_headers = 
    "Authorization: Bearer your_token_here\r\n"
    "X-Access-Token: abc123456\r\n"
    "Cookie: session_id=987654321\r\n";

av_dict_set(&options, "headers", my_headers, 0);

// 打开连接
int ret = avformat_open_input(&pFormatCtx, "https://example.com/video.mp4", NULL, &options);
```

### 2. 将 Token 直接拼接到 URL

有些流媒体服务器（如阿里云、腾讯云或 CDN）支持通过 URL 参数进行校验。这种方式最简单，不需要配置 `AVDictionary`。

- **URL 形式：** `https://api.test.com/live/stream.flv?token=abcdef123456`
- **注意：** 如果 Token 包含特殊字符，确保进行了 **URL 编码**。

### 3. 处理动态变化的 Cookie

如果你需要 FFmpeg 在多个请求之间（比如 HLS 的索引文件和分片文件）保持 Cookie 状态，可以启用 `cookies` 选项。

```c
// 开启 Cookie 支持
av_dict_set(&options, "cookies", "1", 0);
```

### 4. 常见验证场景及其配置表

| **验证类型**       | **字典 Key** | **格式示例 (Value)**                                      |
| ------------------ | ------------ | --------------------------------------------------------- |
| **Bearer Token**   | `headers`    | `"Authorization: Bearer <TOKEN>\r\n"`                     |
| **Basic Auth**     | `headers`    | `"Authorization: Basic <BASE64_ENCODED_CREDENTIALS>\r\n"` |
| **自定义 Header**  | `headers`    | `"X-My-Auth: 12345\r\n"`                                  |
| **Referer 防盗链** | `referer`    | `"https://your-website.com/"`                             |
| **Cookie**         | `headers`    | `"Cookie: name=value; name2=value2\r\n"`                  |
| **User-Agent**     | `user_agent` | `"YourAppName/1.0"`                                       |

### 5. 调试技巧：查看请求头

如果你发现添加了 Token 依然返回 `403 Forbidden` 或 `401 Unauthorized`，可以开启 FFmpeg 的日志回调来查看它到底发出了什么样的请求：

```c
// 设置日志级别为 DEBUG 级别，可以看到完整的 HTTP Header 交互
av_log_set_level(AV_LOG_DEBUG);
```

**关键提示：**

- **内存管理**：`avformat_open_input` 执行完后，FFmpeg 会复制一份 `options` 中的内容，因此你可以放心地调用 `av_dict_free(&options)`。
- **多行 Header**：在 `headers` 字符串中，每一行**必须**以 `\r\n` 结尾，否则 FFmpeg 可能无法正确解析后续的 Header。
