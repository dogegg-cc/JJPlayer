# AVFormatContext

在 FFmpeg 的世界里，如果说有哪些结构体是绝对的“一号男主角”，那非 **`AVFormatContext`** 莫属。

它是 FFmpeg 中解封装（Demuxing，把 MP4/MKV 等文件拆解成音频和视频流）和封装（Muxing，把音视频流打包成文件）的**总上下文**。你可以把它看作是一个**超级大管家**，几乎所有与多媒体文件、网络流整体相关的信息，全部都由它来掌管。

### 1. 它的核心地位：承上启下

在 FFmpeg 的架构中，`AVFormatContext` 就像一个枢纽，它一边连着底层的 I/O 协议（文件或网络），一边连着文件内部包含的各个具体的音视频流（Streams）。

```
           [ 文件(Local/HTTPS) / 硬件设备 ]
                          │
                          ▼ (底层I/O: AVIOContext)
               ┌──────────────────────┐
               │   AVFormatContext    │ ◄── (你的主要控制和查询对象)
               └──────────────────────┘
                          │
         ┌────────────────┴────────────────┐
         ▼                                 ▼
   [ 视频流: AVStream ]              [ 音频流: AVStream ]
         │                                 │
   [ 解码器: AVCodecContext ]        [ 解码器: AVCodecContext ]
```

### 2. 核心成员变量详解

`AVFormatContext` 内部的结构非常庞大，但作为开发者，你最常打交道的核心字段主要有以下几个：

#### ① 基础与核心控制

- **`const AVInputFormat \*iformat`**（解封装时使用）：

  指明当前打开的文件的**输入封装格式**（例如 MP4、FLV、MKV、AVI 等）。

- **`const AVOutputFormat \*oformat`**（封装时使用）：

  指明当前正在写入的文件的**输出封装格式**。

- **`AVIOContext \*pb`**：

  底层 I/O 字节流的上下文。无论是读本地文件还是读 HTTPS 网络流，底层的二进制数据读取和缓存管理都是由它来对接的。

#### ② 媒体流信息

- **`unsigned int nb_streams`**：

  当前文件中包含的**流的总数量**（比如：1个视频流 + 1个音频流 + 1个字幕流 = 3）。

- **`AVStream streams`**：

  一个指针数组，里面存放了所有流的指针。通过 `streams[i]` 可以访问到每一个具体的 `AVStream`（从而获取分辨率、采样率等）。

#### ③ 全局元数据

- **`int64_t duration`**：

  整个文件的**总时长**（注意：它的单位是 `AV_TIME_BASE`，即微秒 $\mu s$。转换为秒需要除以 $1,000,000$ 或者使用公式 `duration / AV_TIME_BASE`）。

- **`int64_t bit_rate`**：

  整个文件的**全局码率**（单位是 bps，即 bits/s）。如果是直播流或某些无法预知的流，该值可能为 0。

- **`AVDictionary \*metadata`**：

  文件的元数据标签（Tags），比如歌曲的名、歌手、专辑、电影的拍摄日期等。

#### ④ 探测与网络控制

- **`int64_t probesize` / `int64_t max_analyze_duration`**：

  我们在讲 `avformat_find_stream_info` 时提到的两个控制参数。用于控制探测文件格式和流信息时，最多可以读取多少字节、分析多长时间的媒体数据。

- **`AVIOInterruptCB interrupt_callback`**：

  **极其重要的中断回调函数。** 当你在读取 HTTPS 网络流或者阻塞式拉流时，如果网络突然断开导致程序卡死，你可以通过这个回调函数让 `avformat_open_input` 或 `av_read_frame` 立刻强退，实现超时控制。

### 3. 生命周期与内存管理

因为 `AVFormatContext` 是一个复杂的结构体，**千万不能直接在栈上定义（如 `AVFormatContext ctx;`）**，必须通过 FFmpeg 提供的 API 在堆上动态分配，并严格遵守其生命周期：

#### 🔓 解封装（读文件/流）的生命周期：

```c
// 1. 创建上下文指针，初始化为 NULL
AVFormatContext *pFormatCtx = NULL; 

// 2. 打开输入源（函数内部会自动分配内存并填充初始信息）
int ret = avformat_open_input(&pFormatCtx, "https://...", NULL, NULL);

// 3. 获取详细流信息（进一步填充内部的 streams 字段）
avformat_find_stream_info(pFormatCtx, NULL);

// ... 你的业务逻辑：读取数据包 av_read_frame ...

// 4. 彻底释放（函数内部会释放 pb、streams 以及 pFormatCtx 自身）
avformat_close_input(&pFormatCtx); 
```

#### 🔒 封装（写文件/录制）的生命周期：

```c
AVFormatContext *pFormatCtx = NULL;

// 1. 为输出分配上下文
avformat_alloc_output_context2(&pFormatCtx, NULL, NULL, "output.mp4");

// ... 你的业务逻辑：添加流、写文件头、写数据包 ...

// 2. 彻底释放
avformat_free_context(pFormatCtx);
```

### 4. 常见避坑指南

1. **别漏了 `avformat_close_input`**：

   只要 `avformat_open_input` 成功了，最后就**必须**调用 `avformat_close_input`。如果你中间发生错误直接 `return` 掉了，或者误用了 `avformat_free_context`，会导致底层的网络连接（Socket）或文件句柄没有被正确关闭，从而引发严重的内存和资源泄漏。

2. **时长单位的陷阱**：

   初学者经常会直接打印 `pFormatCtx->duration`，然后疑惑为什么一个 3 分钟的视频，时长显示是一亿多。请记住，FFmpeg 内部时间基准 `AV_TIME_BASE` 是 $1,000,000$。

   ```c
   double seconds = pFormatCtx->duration / (double)AV_TIME_BASE;
   printf("视频时长: %.2f 秒\n", seconds);
   ```

3. **不要手动去修改 `nb_streams` 或 `streams` 数组**：

   在解封装时，这些属于只读数据，由 FFmpeg 内部统一管理。

### 总结

`AVFormatContext` 是你操控媒体文件的“方向盘”。当你拿到了它，就等于拿到了整张地图。接下来，你就可以根据 `nb_streams` 遍历地图上的每一条路（`AVStream`），去寻找真正的音视频宝藏（`AVPacket` / `AVFrame`）了。



# AVCodecContext

如果说 `AVFormatContext` 是掌控大局的“总管”（负责拆解容器），那么 **`AVCodecContext`** 就是干脏活累活的“核心技术骨干”——它负责**解码（Decode）\**和\**编码（Encode）**。

无论是把压缩的 H.264/H.265 视频数据还原成能显示的 YUV/RGB 画面，还是把麦克风录制的 PCM 音频打包成 AAC，全部都要通过 `AVCodecContext` 这一层。

### 1. 它的核心地位：承上启下

在 FFmpeg 的完整管线中，它处于整个多媒体处理的核心位置：

```
       [ 容器/文件 ] ──► [ 压缩数据包: AVPacket ]
                                │
                                ▼
                    ┌──────────────────────┐
                    │    AVCodecContext    │ ◄── (你的核心控制对象)
                    └──────────────────────┘
                                │
                                ▼
       [ 渲染/播放 ] ◄── [ 原始画面/声音: AVFrame ]
```

### 2. 核心成员变量详解

`AVCodecContext` 同样是一个极其庞大的结构体，它同时服务于**编码**和**解码**。根据你的应用场景，你需要关注不同的核心字段：

#### ① 通用核心参数

- **`const AVCodec \*codec`**:

  当前使用的解码器/编码器（例如指向 H.264 解码器或 AAC 编码器的实体）。

- **`enum AVMediaType codec_type`**:

  媒体类型，用于区分当前是视频（`AVMEDIA_TYPE_VIDEO`）、音频（`AVMEDIA_TYPE_AUDIO`）还是字幕。

#### ② 视频专属参数（解码后/编码前）

- **`int width` / `int height`**: 视频的宽高（分辨率）。

- **`enum AVPixelFormat pix_fmt`**:

  像素格式（如常见的 `AV_PIX_FMT_YUV420P`、`AV_PIX_FMT_NV12` 或 RGB24）。

- **`AVRational time_base`**:

  **极其重要的时间基（Time Base）**。它决定了音视频帧的时间戳（PTS/DTS）如何换算成现实中的秒。

#### ③ 音频专属参数

- **`int sample_rate`**: 音频采样率（如 44100Hz、48000Hz）。

- **`enum AVSampleFormat sample_fmt`**:

  音频采样格式（如 16位整型 `AV_SAMPLE_FMT_S16`，或浮点型 `AV_SAMPLE_FMT_FLTP`）。

- **`AVChannelLayout ch_layout`**:

  声道布局结构体（包含声道数和具体的声道配置，如立体声、5.1声道）。

#### ④ 编码专属（压缩控制）

- **`int64_t bit_rate`**: 目标码率（控制视频/音频压缩后的体积和画质）。
- **`int gop_size`**: GOP（画面组）大小，即两个 I 帧（关键帧）之间的最大距离。

### 3. 解码流程中的经典生命周期

在 FFmpeg 4.x/5.x/6.x 及更新版本中，官方极其推荐使用 `codecpar`（解码器参数）来初始化 `AVCodecContext`。以下是标准的**解码初始化与释放流程**：

```c
// 1. 找到对应的解码器（假设 stream 是从 AVFormatContext 中拿到的视频流）
const AVCodec *pCodec = avcodec_find_decoder(stream->codecpar->codec_id);
if (!pCodec) {
    printf("找不到对应的解码器\n");
    return -1;
}

// 2. 为 AVCodecContext 分配堆内存
AVCodecContext *pCodecCtx = avcodec_alloc_context3(pCodec);
if (!pCodecCtx) return -1;

// 3. 将流中的参数（如宽高、采样率）复制到解码上下文中
avcodec_parameters_to_context(pCodecCtx, stream->codecpar);

// 4. 打开解码器
if (avcodec_open2(pCodecCtx, pCodec, NULL) < 0) {
    printf("无法打开解码器\n");
    return -1;
}

// ... 你的核心循环：avcodec_send_packet() 和 avcodec_receive_frame() ...

// 5. 彻底释放内存并关闭解码器
avcodec_free_context(&pCodecCtx);
```

### 4. 经典的数据处理“冲刷”机制（Send / Receive）

有了 `AVCodecContext` 之后，怎么让它工作？FFmpeg 使用了一套非阻塞的 **发送/接收** 异步 API：

```
       [ 压缩数据 AVPacket ] ──► avcodec_send_packet(ctx, packet)
                                            │
                                            ▼  (内部解码队列)
      avcodec_receive_frame(ctx, frame) ──► [ 原始数据 AVFrame ]
```

- **为什么要设计成这样？**

  因为视频存在 B 帧（双向预测帧）。你喂给解码器 1 个 `AVPacket`，解码器内部可能由于依赖关系**无法立刻吐出**画面，或者可能在遇到某些关键帧时**一口气吐出多个** `AVFrame`。因此发送和接收是分离的。

### 5. 避坑与高级技巧

1. **废弃的旧 API 陷阱**：

   如果你在网上看一些老旧的教程，会看到 `stream->codec`。**请立刻删掉它。** 该字段在数个版本前已被彻底移除。现在必须通过 `stream->codecpar` 结合 `avcodec_parameters_to_context` 来初始化上下文。

2. **多线程解码加速**：

   `AVCodecContext` 默认是单线程解码的，解析 4K 视频时可能会卡顿。你可以在调用 `avcodec_open2` **之前**开启多线程：

   

   ```c
   pCodecCtx->thread_count = 0; // 设为 0 表示让 FFmpeg 自动根据你的 CPU 核心数决定线程数
   pCodecCtx->thread_type = FF_THREAD_FRAME; // 帧级多线程
   ```

3. **内存释放安全**：

   关闭解码器请使用 `avcodec_free_context(&pCodecCtx)`。它比旧的 `avcodec_close()` 更安全，因为它不仅会关闭解码器，还会把分配的 `AVCodecContext` 结构体内存整体释放，并将指针置为 `NULL`。

### 总结对比

| **结构体**            | **负责的生命周期**              | **核心处理对象**                                     |
| --------------------- | ------------------------------- | ---------------------------------------------------- |
| **`AVFormatContext`** | 文件的输入/输出、解封装、流合并 | `AVStream`, `AVIOContext`                            |
| **`AVCodecContext`**  | 数据的压缩与解压缩、格式转换    | `AVPacket` (压缩) $\leftrightarrow$ `AVFrame` (原始) |



# AVFrame

在 FFmpeg 的核心家族中，如果说 `AVPacket` 存的是被高度压缩的“数字罐头”，那么 **`AVFrame`** 装的就是打开罐头后、实打实呈现在眼前的“新鲜饕餮大餐”。

`AVFrame` 代表的是**未压缩的原始媒体数据**（Raw Media Data）。

- **对于视频**：它是一帧完整的、可以直接送去显卡渲染的画面（如 YUV420P、NV12、RGB24 格式）。
- **对于音频**：它是一段可以直接送去声卡播放的 PCM 采样数据。

### 1. 核心成员变量：数据怎么存？

`AVFrame` 内部最让人头疼的就是数据指针的存储方式，它是为多通道/多平面（Planar）数据设计的。

```c
uint8_t *data[AV_NUM_DATA_POINTERS];
int linesize[AV_NUM_DATA_POINTERS];
```

#### ① `data` 指针数组

存放实际像素或音频采样的内存地址。

- **视频（以 YUV420P 为例）**：它是**平面格式（Planar）**。
  - `data[0]` 指向一整张 Y（亮度）分量的内存。
  - `data[1]` 指向 U（色度）分量的内存。
  - `data[2]` 指向 V（色度）分量的内存。
- **视频（以 RGB24 为例）**：它是**打包格式（Packed）**。R、G、B 交织在一起。
  - 所有数据都挤在 `data[0]` 里。
- **音频（以立体声 PCM 为例）**：
  - 如果是 **交织格式（Packed，如 S16）**：左右声道交替排列，全在 `data[0]`。
  - 如果是 **带 P 的平面格式（Planar，如 S16P）**：`data[0]` 是左声道，`data[1]` 是右声道。

#### ② `linesize` 跨度/步长数组

表示每一行数据的**字节数**。

- **关键陷阱**：视频的一行 `linesize[0]` **并不一定等于视频的宽度（Width）**！为了提高 CPU/GPU 的内存对齐效率（比如 16 或 32 字节对齐），FFmpeg 经常会在每一行的末尾塞一些“填料（Padding）”。
- 在把 `AVFrame` 里的画面复制出来（比如转成 OpenCV 的 Mat 或者写入文件）时，必须使用 `linesize` 来逐行复制，绝不能认为内存是完全连续的。

#### ③ 时间戳与控制

- **`int64_t pts`**：

  Presentation Time Stamp（显示时间戳）。这一帧画面应该在什么时间点被播放出来，单位由对应的 `AVStream` 的 `time_base` 决定。

- **`int width, height`** / **`int sample_rate, nb_samples`**：

  这一帧画面具体的分辨率，或者这段音频的采样率和单通道采样点数。

- **`int key_frame`**：

  标记这一帧是不是关键帧（I 帧）。

### 2. 生命周期与内存引用计数（极其重要）

原始的音视频数据非常庞大（一帧 1080P 的 YUV420P 画面大约要 3MB 内存）。如果频繁地分配和销毁内存，程序很快就会卡死。因此，`AVFrame` 采用了 **引用计数（Reference Counting）** 机制。

```
     [ AVFrame 结构体 ] (轻量)
            │
            ▼ 指向
     [ AVBufferRef ] ───► [ 真正的超大原始数据内存 ] (重量)
                          (引用计数 = 1)
```

当你调用 `av_frame_ref()` 复制一帧时，FFmpeg **不会**去拷贝那 3MB 的大内存，而是让两个 `AVFrame` 结构体指向同一个内存块，并将引用计数加 1。

#### 🛠️ 标准生命周期代码：

```c
// 1. 在堆上分配 AVFrame 结构体（此时还没有分配实际的数据内存）
AVFrame *frame = av_frame_alloc();

// 2. 解码器往里面灌数据
// 函数内部会引发引用计数逻辑：
// 发现内部为空 -> 分配大内存 -> 写入YUV数据 -> 引用计数设为 1
int ret = avcodec_receive_frame(codec_ctx, frame); 

if (ret == 0) {
    // 3. 使用你的数据（比如送去渲染、或者转码）
    printf("成功解码一帧，PTS = %ld\n", frame->pts);
    
    // 4. 清空释放
    // 注意：它不会直接销毁结构体，而是将大内存的引用计数减 1。
    // 如果计数变为 0，则真正释放 3MB 的大内存。同时将结构体内部字段重置。
    av_frame_unref(frame); 
}

// 5. 彻底销毁结构体（通常在播放结束、退出程序时调用）
av_frame_free(&frame);
```

### 3. 常见避坑指南

1. **忘记调用 `av_frame_unref`**：

   在你的解码 `while` 循环里，每次成功拿到 `frame` 并处理完后，**必须**调用 `av_frame_unref(frame)`。如果不调用，下一次 `avcodec_receive_frame` 就会导致旧的内存无法释放，程序运行几秒钟就会因为内存泄露（OOM）直接崩溃。

2. **硬拷贝（Deep Copy）的正确姿势**：

   如果你需要把这一帧画面丢到另一个线程去慢慢处理，直接 `frame2 = frame1` 是致命的错误。你应该：

   

   ```c
   AVFrame *frame2 = av_frame_alloc();
   av_frame_ref(frame2, frame1); // 仅仅增加引用计数，极其高效
   ```

   如果你真的想要一份完全独立的、可以任意修改像素的拷贝：

~~~c
    AVFrame *frame2 = av_frame_alloc();
    frame2->format = frame1->format;
    frame2->width = frame1->width;
    frame2->height = frame1->height;
    av_frame_get_buffer(frame2, 0); // 分配全新的大内存
    av_frame_copy(frame2, frame1);  // 真正复制像素数据
    ```

### 四大核心结构体大通关 🏆

恭喜你！到这里你已经把 FFmpeg 最核心的四大组件全部梳理完毕了。我们用一句话来串联它们的合作关系：

> 通过 **`AVFormatContext`** 打开输入文件，从中找到视频流并利用其参数初始化 **`AVCodecContext`** 解码器。随后我们在循环中读取封装好的 **`AVPacket`**（压缩包），将其喂给解码器，最终吐出可以用于播放渲染的 **`AVFrame`**（原始肉眼可见画面）。

你下一步是准备把拿到的 `AVFrame` 通过 SDL2/OpenGL 渲染到屏幕上，还是准备写进另一个文件里做视频剪辑/转码？
~~~

# AVPacket

如果说 `AVFrame` 存放的是解压后、肉眼可见的“饕餮大餐”，那么 **`AVPacket`** 装的就是解压前、处于运输状态的“数字罐头”。

`AVPacket` 代表的是**高度压缩的媒体数据**（Coded/Compressed Media Data）。

- **对于视频**：它通常包含一个完整的 H.264/H.265 **I 帧**（关键帧）、**P 帧**或 **B 帧**的压缩码流。
- **对于音频**：它通常包含一个或多个连续的 AAC / MP3 音频帧。

在数据流向中，它是 `AVFormatContext`（解封装）和 `AVCodecContext`（解码器）之间的**核心中转站**。

### 1. 核心成员变量：压缩数据怎么存？

由于数据是压缩过的，`AVPacket` 内部的结构相比 `AVFrame` 要直观得多，它的核心就是一段连续的二进制缓冲区：

- **`uint8_t \*data`**：

  指向存储压缩码流的内存缓冲区的指针（比如 H.264 的 NALU 数据）。

- **`int size`**：

  压缩数据的实际字节大小（Byte）。

- **`int stream_index`**：

  标识这个数据包属于哪个流。例如，如果 `stream_index == 0`，代表它是视频包；如果是 `1`，代表它是音频包。你可以根据它把数据包分发给不同的解码器。

#### ⏰ 时间戳控制（面试高频考点）

- **`int64_t pts` (Presentation Time Stamp)**：

  显示时间戳。告诉播放器这包数据解码后，**应该在什么时间点显示/播放**给用户看。

- **`int64_t dts` (Decoding Time Stamp)**：

  解码时间戳。告诉解码器**应该在什么时间点开始解码**这包数据。

  > **为什么需要两个时间戳？**
  >
  > 因为视频中存在 **B 帧（双向预测帧）**。B 帧需要参考后面的 P 帧才能完成解码。这就导致：**必须先解码 P 帧，才能解码 B 帧，但 B 帧要先于 P 帧显示。**
  >
  > 也就是说，DTS（解码顺序）和 PTS（显示顺序）在有 B 帧的情况下是不一样的。

- **`int64_t duration`**：

  当前这包数据对应的媒体流时长（单位同样是对应流的 `time_base`）。

- **`int flags`**：

  标志位。最常用的是 `AV_PKT_FLAG_KEY`，用来标记这包数据是不是一个**关键帧（I 帧）**。在做视频快进（Seek）或者生成缩略图时，我们必须先找到带有这个标记的 `AVPacket`。

### 2. 生命周期与内存管理（引用计数）

和 `AVFrame` 类似，`AVPacket` 里的 `data` 缓冲区也采用了**引用计数**机制。因为频繁的内存拷贝是多媒体处理的性能杀手。

```
     [ AVPacket 结构体 ] (轻量，通常在栈上或堆上分配)
            │
            ▼ 指向
     [ AVBufferRef ] ───► [ 真正的压缩码流数据 ] (几KB 到 几百KB)
                          (引用计数控制)
```

#### 🛠️ 标准生命周期代码：

```c
// 1. 分配 AVPacket 结构体内存（此时内部的 data 为 NULL）
AVPacket *pkt = av_packet_alloc();

// 2. 从多媒体文件中读取一包压缩数据
// 函数内部会分配实际的 data 缓冲区，并将引用计数设为 1
while (av_read_frame(pFormatCtx, pkt) >= 0) {
    
    // 3. 根据 stream_index 分流处理
    if (pkt->stream_index == video_stream_idx) {
        
        // 4. 喂给解码器
        int ret = avcodec_send_packet(pCodecCtx, pkt);
        
    }
    
    // 5. 极其重要！清空并释放 AVPacket 内部的 data 缓冲区
    // 它会将引用计数减 1。如果计数归零，彻底释放数据内存。
    // 同时把 pkt 内部的指针重新置空，以便下次循环复用
    av_packet_unref(pkt);
}

// 6. 退出程序或销毁播放器时，彻底释放 AVPacket 结构体本身
av_packet_free(&pkt);
```

### 3. 常见避坑指南

1. **别把 `av_packet_unref` 漏在循环里**：

   `av_read_frame` 每次执行都会为 `pkt->data` 分配全新的内存。如果你在 `while` 循环末尾忘记调用 `av_packet_unref(pkt)`，这包数据的内存就永远失去了释放的机会。程序运行几分钟就会引发严重的内存泄漏。

2. **结构体 vs 指针（旧版本兼容）**：

   在早期的 FFmpeg 遗留代码中（如 3.x 版本），人们经常使用局部变量 `AVPacket pkt; av_init_packet(&pkt);`。

   **在现代 FFmpeg（4.x / 5.x / 6.x）中，这种做法已被彻底废弃！** 现在必须严格使用 `av_packet_alloc()` 和 `av_packet_free()`。

3. **数据的浅拷贝（高效转发）**：

   如果你在做视频服务器、转发流媒体（如把 RTSP 转推到 RTMP），你根本不需要解码。你可以直接用 `av_packet_ref(dest, src)` 增加一次引用计数，然后直接送去封装器（Muxer）写入网络，这个过程几乎不消耗 CPU 性能。

### 🎬 终极完美串联：FFmpeg 核心骨架

现在，你已经将 FFmpeg 的 **五大核心结构体** 全部通关！我们用一段最简洁、最直观伪代码，把它们怎么组合、怎么协同工作的完整全貌展现出来：

```c++
AVFormatContext *fmt_ctx = NULL;
avformat_open_input(&fmt_ctx, "https://...", NULL, NULL); // 1. 打开大门
avformat_find_stream_info(fmt_ctx, NULL);                 // 2. 探明虚实

// 3. 找到视频流，并初始化解码上下文
int v_idx = av_find_best_stream(fmt_ctx, AVMEDIA_TYPE_VIDEO, -1, -1, NULL, 0);
AVCodecContext *codec_ctx = avcodec_alloc_context3(avcodec_find_decoder(fmt_ctx->streams[v_idx]->codecpar->codec_id));
avcodec_parameters_to_context(codec_ctx, fmt_ctx->streams[v_idx]->codecpar);
avcodec_open2(codec_ctx, NULL, NULL);                      // 4. 唤醒解码器

AVPacket *pkt = av_packet_alloc();                         // 5. 准备“数字罐头”
AVFrame *frame = av_frame_alloc();                         // 6. 准备“大餐盘子”

// 7. 主循环：读取与解码
while (av_read_frame(fmt_ctx, pkt) >= 0) {
    if (pkt->stream_index == v_idx) {
        
        avcodec_send_packet(codec_ctx, pkt);               // 8. 喂入压缩包(AVPacket)
        
        while (avcodec_receive_frame(codec_ctx, frame) == 0) {
            // 9. 成功榨出原始画面(AVFrame)！在这里拿去渲染、人脸识别或转码
            printf("渲染画面 PTS: %ld\n", frame->pts);
            
            av_frame_unref(frame);                         // 清空盘子
        }
    }
    av_packet_unref(pkt);                                  // 扔掉空罐头
}

// 10. 完美的谢幕，打扫战场
av_frame_free(&frame);
av_packet_free(&pkt);
avcodec_free_context(&codec_ctx);
avformat_close_input(&fmt_ctx);
```

这就是绝大多数商业播放器、剪辑软件、推流工具底层的核心骨架。
